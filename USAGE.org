This document describes the working day of an architectural assessment with Blueprint.el. It is not an API reference: it is a practical guide that follows the method in docs/method/method.org.

Audience: architects and consultants using Blueprint.el on an engagement.
#+end_comment

* Introduction

Blueprint.el is an Emacs package for producing the architectural documentation of software systems, typically existing ones that have none. The underlying method is reverse engineering: the source code is the primary source, and the documentation is rebuilt from it step by step. The same structure also works for a system being designed (see the method, "Using the method on a new system").

The templates, the headings they create and the markers are in Italian for now. Full English support and localized templates are planned (PLAN.org, phase 11).

** Mental model

The output document is a =master.org= that assembles satellite files with =#+INCLUDE=. Every component has its own directory with three self-contained files:

| File                 | Content                                   | Master part |
|----------------------+-------------------------------------------+-------------|
| =arc42.org=          | Software architecture (arc42)             | Part II     |
| =functional.org=     | Functional specifications, business rules | Part III    |
| =infrastructure.org= | Infrastructure inventory                  | Part IV     |

The files that cover the whole project live at the project root:

| File/Directory   | Content                               | Master part |
|------------------+---------------------------------------+-------------|
| =enterprise/=    | Aggregate view across systems         | Part I      |
| =nfr/=           | Quality scenarios, constraints, risks | Part V      |
| =glossary.org=   | Domain glossary                       | Part 0      |
| =references.org= | Sources, interviews, documents        | References  |

The main menu is on =C-c b=.

** Prerequisites

- Emacs 29 or later
- Blueprint.el installed (see "Installation" in the README; the package is not on MELPA yet)
- PlantUML to render the diagrams (optional, recommended)
- Graphviz for the dependency graph (optional)

To render PlantUML inline in Org mode, add to your =init.el=:

#+begin_src emacs-lisp
  (setq org-plantuml-jar-path "/path/to/plantuml.jar")
  (add-to-list 'org-src-lang-modes '("plantuml" . plantuml))
  (org-babel-do-load-languages 'org-babel-load-languages
                               '((plantuml . t)))
#+end_src

* Structure of the output document

The master document follows the six-part structure of the method:

| Part | Title                     | Primary audience              |
|------+---------------------------+-------------------------------|
| 0    | Premises                  | Everyone                      |
| I    | Enterprise architecture   | Executives, senior architects |
| II   | Architecture by component | Architects, senior developers |
| III  | Functional specifications | Analysts, product owners      |
| IV   | Infrastructure inventory  | IT operations, system admins  |
| V    | NFR, constraints, risks   | Architects, IT management     |

Each part declares its audience, so every reader can go straight to their own without crossing material that does not concern them.

* Workflow 0: starting the project

/When: at the start of the engagement, in the first working session./

** Step 1: create the structure

#+begin_src
M-x blueprint-init  (or: C-c b I)
#+end_src

Creates the project structure in the current directory. The command is idempotent: running it again does not overwrite existing files.

What it creates:

#+begin_example
master.org
glossary.org
references.org
enterprise/
  context.org
  dependencies.org
nfr/
  quality-scenarios.org
  constraints.org
  risks.org
_archive/
.blueprint/
  blueprint-version.org
  components/
#+end_example

The first time it runs interactively, =blueprint-init= also copies the system templates to =~/.config/blueprint/templates/=, where they become your personal defaults.

** Step 2: customize the templates (optional)

If the project needs its own templates (extra sections, different notations, text prepared for the client):

#+begin_src
M-x blueprint-template-migrate  (or: C-c b M)
#+end_src

Copies the system templates into =.blueprint/templates/=. From then on the project's templates take precedence over the personal and system ones.

Available templates: =component.org=, =arc42-enterprise.org=, =functional.org=, =infrastructure.org=, =adr.org=, =master.org=, =glossary.org=, =references.org=, =enterprise-context.org=, =enterprise-dependencies.org=, =nfr-quality.org=, =nfr-constraints.org=, =nfr-risks.org=.

** Step 2b: choose the name of the data directory (optional)

The project's data directory (components, ADRs, local templates) is called =.blueprint/= by default. If the layout has to match what a site generator or a build tool expects, set =blueprint-directory-name= to another name or to a nested relative path, for example =content/blueprint=, globally (=init.el= or Customize):

#+begin_src emacs-lisp
(setq blueprint-directory-name "content/blueprint")
#+end_src

The variable is also marked safe as a directory-local, but a value in =.dir-locals.el= only reaches buffers visiting a file of the project: commands run from buffers without a file (dashboard, result buffers) still see the global value.

A project that still has =.blueprint/= keeps working after the change: Blueprint falls back to it and says so once per session. To rename it:

#+begin_src
M-x blueprint-migrate-directory  (or: C-c b m)
#+end_src

The command shows the plan and asks for confirmation. Then it renames the directory (with =git mv= if git tracks it) and rewrites every =file:= link and every =#+INCLUDE:= / =#+SETUPFILE:= path in the project's Org files that the rename would break, including links from files inside the moved directory to files outside it. Mentions in free text (prose, =:file= arguments of source blocks) are only listed in the report buffer, to be fixed by hand.

** Step 3: write Part 0 of the master

Open =master.org= and fill in the sections of Part 0 by hand:
- purpose of the document;
- scope of the assessment (components included and excluded);
- how the information was gathered;
- reference period and versions analyzed.

These sections are editorial and need input specific to the project.

* Workflow 1: managing the scope

/When: once the list of components to document has been agreed with the client./

** Add a component

#+begin_src
M-x blueprint-add-component  (or: C-c b A)
Component name: order-service
#+end_src

Creates =.blueprint/components/order-service/= with:
- =arc42.org=, always;
- =functional.org=, if the template exists;
- =infrastructure.org=, if the template exists.

The name is turned into a slug (lower case, hyphens). Use names from the client's domain language, not internal code names (=billing= rather than =billing-service-v2=).

With a prefix argument (=C-u C-c b A=) the command also asks which arc42 template to use: =component.org= (standard) or =arc42-enterprise.org=, which adds enterprise context, stakeholders and points of contact, and compliance to the arc42 sections, for the major components of large engagements. Without the prefix the behavior is the standard one.

** Declare dependencies

Open the component's =arc42.org= and fill in the keyword:

#+begin_example
#+BLUEPRINT_DEPENDS: auth-service database cache
#+end_example

This line is the source for the generated C4 diagram and for spotting anomalies in the dependencies (isolated components, cycles).

Systems outside the scope (black boxes) go into the C4 diagram as =System_Ext=, not as Blueprint components.

The lifecycle of a component is a separate axis from the scope: =#+BLUEPRINT_LIFECYCLE: draft|active|deprecated|archived= (=active= when the keyword is missing, so older components stay =active=). The dashboard shows it in the =Life= column, and the linter warns when an =active= component depends on a =deprecated= one or has open FIXMEs (=blueprint-lint-lifecycle-checks=, on by default).

** Rename a component

#+begin_src
M-x blueprint-rename-component  (or: C-c b R)
#+end_src

Updates every occurrence of the name in the =BLUEPRINT_DEPENDS= of the other components.

** Delete a component

#+begin_src
M-x blueprint-delete-component  (or: C-c b X)
#+end_src

Asks for confirmation and deletes the component's directory. The confirmation warns when other components still declare the name in =#+BLUEPRINT_DEPENDS:=: those dependencies stay (a human decides), and the linter reports them as dangling until they are removed by hand. After the confirmation, before deleting the directory, it removes the component's =#+INCLUDE= lines and headings from the synchronized sections of =master.org= (the next =blueprint-sync= restores the exact format of the section).

** Check the scope

#+begin_src
M-x blueprint-lint  (or: C-c b L)
#+end_src

Reports dependencies on components that do not exist, missing mandatory sections and missing template files.

* Workflow 2: architecture by component (arc42)

/When: for each component, once there is access to the source code./

** Recommended order: top down

1. =Context and Scope= first (what it does, who uses it, neighboring systems).
2. Then =Building Blocks= (internal structure, C4 level 2 or 3).
3. Then =Runtime Behavior= (main flows).
4. Then =Constraints= and =Solution Strategy=, reconstructed from the code.
5. =Risks= and =Open Questions= last: they come out of the analysis.

** Open a component's documents

Every component has up to three documents, one for each part of the deliverable: =arc42.org= (Part II), =functional.org= (Part III) and =infrastructure.org= (Part IV), all in =.blueprint/components/<name>/=. To open one:

- =M-x blueprint-visit-component= (=C-c b j=) asks for the component and then for the document among those that exist, with =arc42.org= preselected; a component with only =arc42.org= opens without asking. The choices also include the other files of the document (=master.org=, glossary, =enterprise/*=, =nfr/*=, references), shown with their path relative to the root: choosing one opens it directly.
- The component list (=C-c b l=): the Documents column shows which files each component has; ~RET~ asks which one to open, =a=, =f= and =i= open =arc42.org=, =functional.org= and =infrastructure.org= directly.
- The dashboard (=C-c b B=): ~RET~ on a component asks for the document like =blueprint-visit-component=; on the row of another file of the document it opens that file.

** Runtime flows

Add a documented runtime flow (use cases plus a sequence diagram):

#+begin_src
M-x blueprint-runtime-add-flow  (or: C-c b r)
Component: order-service
Flow name: checkout
#+end_src

Inserts under =* Runtime Behavior= a subheading with:
- a use case diagram, for non-technical stakeholders;
- a sequence diagram, for technical teams.

Both are PlantUML templates to complete.

** Business processes

Add a business process with several actors, as a UML activity diagram with swimlanes. It is different from a runtime flow: a flow describes how messages travel between system components, a business process describes which actor performs each step.

#+begin_src
M-x blueprint-runtime-add-process  (or: C-c b b)
Component: order-service
Process name: returns handling
#+end_src

Inserts under =* Processi di business= (created if missing) a subheading with a swimlane PlantUML block to complete (lanes, steps, a sample decision point).

** Mark a component out of scope

Set =#+BLUEPRINT_STATUS:= in the header of =arc42.org= (=in-scope= when missing, so components created before this feature behave as before):

#+begin_src org
#+BLUEPRINT_STATUS: out-of-scope
#+end_src

Values: =in-scope= (default), =out-of-scope=, =tbd=. =blueprint-lint= reports an =in-scope= component that depends on an =out-of-scope= one; the dashboard has a "Scope" column and a filter (=C-c b o=, or =O= in the dashboard buffer) to review only the components outside the scope. The reason for the exclusion is written by hand in Part 0 of the master: the keyword only records the state, not the reason.

** Markers while writing

Use the markers defined by the method:

| Marker                   | When to use it                                         |
|--------------------------+--------------------------------------------------------|
| =[DA VALIDARE]=          | To validate: written, not yet checked with the client  |
| =[FINDING]=              | A discrepancy between actual and expected behavior     |
| =[APPROVATO YYYY-MM-DD]= | Approved by the client's owner on that date            |
| =[FONTE: X]=             | The source (for example, FONTE: interview with J. Doe) |

The markers =QUESTION=, =TBD=, =FIXME=, =[DA VALIDARE]= and =[DA REVISIONARE]= are picked up by the health score and lower the project's score; =[FINDING]= is counted but carries no penalty, because it is a result of the assessment, not an open point.

Only markers in the text that the export actually shows count. Ignored: subtrees with an exclusion tag (=:noexport:= or those listed in =#+EXCLUDE_TAGS:=), COMMENT subtrees, src/example/export/comment blocks, comment lines and verbatim/code markup (writing ==[FINDING]== quotes the marker without creating one). The match is case-sensitive. File keywords such as =#+STATUS: [DA VALIDARE]= still count. That is why the =:noexport:= guides in the templates, with their sample data, do not weigh on the score.

** Open questions during the analysis

#+begin_src
M-x blueprint-add-question  (or: C-c b Q)
Component: order-service
Question: Who authorizes a refund when the payment is already booked?
#+end_src

Questions go into the component's =* Open Questions= section and count in the health score (weight 3 for every unresolved =QUESTION=).

* Workflow 3: functional specifications

/When: after a first reading of the code, to translate the technical logic into the language of the domain./

The goal is specifications that an analyst without a technical background can read, precise enough to reimplement the logic without losing anything.

** Structure of functional.org

=functional.org= is organized as:
- =* Aree funzionali=: functional areas of the domain (for example, Orders, Invoicing)
  - =** Area=: one subsection per area
    - =*** Feature=: a single function or business rule, with inputs, outputs and rules
- =* Entità di dominio=: business objects (not database tables)
- =* Punti di integrazione=: flows in and out of other systems
- =* Open Questions=

** Add a functional area

#+begin_src
M-x blueprint-functional-add-area  (or: C-c b a)
Component: order-service
Area name: Order management
#+end_src

** Add a feature

#+begin_src
M-x blueprint-functional-add-feature  (or: C-c b f)
Component: order-service
Area: Order management
Feature name: Net amount calculation
#+end_src

Inserts a skeleton with purpose, inputs, outputs, business rules, calculation logic, validation rules and edge cases.

** Add a domain entity

#+begin_src
M-x blueprint-functional-add-entity  (or: C-c b e)
Component: order-service
Entity name: Order
#+end_src

Inserts an attribute table and a PlantUML block for the ER diagram.

** Add an integration point

#+begin_src
M-x blueprint-functional-add-integration  (or: C-c b i)
Component: order-service
Integration name: Sending invoices to the billing system
#+end_src

Inserts a metadata table (direction, counterpart, frequency) and a subsection to document the structure of the exchanged payload.

** Principle: independent of the technology

Functional specifications do not mention classes, methods, tables or endpoints. Always rename technical variables with business names:
- =order.total_amount_cents= becomes "Order total (euro cents)";
- =ENUM Status { PENDING, CONFIRMED }= becomes "Order state: pending, confirmed".

* Workflow 4: infrastructure inventory

/When: with access to the environments or to the deployment scripts (Dockerfile, Kubernetes, Terraform)./

=infrastructure.org= is mostly written by hand: its sources are infrastructure configurations, not application code.

** Recommended sources

In order of reliability:
1. Terraform, Pulumi or CloudFormation scripts, the most precise source
2. Kubernetes manifests, Docker Compose files
3. CI/CD pipeline definitions
4. An interview with the system administrator or DevOps engineer

** Sections to fill in

Open =.blueprint/components/<name>/infrastructure.org= and fill in:

- =* Inventario=: a table of hosts and services: name, role, OS or runtime, version, environment, owner
- =* Deployment view=: a PlantUML deployment diagram (nodes, containers, databases)
- =* Dipendenze infrastrutturali=: ports, protocols, direction, whether mandatory
- =* Configurazione rilevante=: parameters with an architectural impact (pool sizes, timeouts, failover)
- =* Ambienti=: differences between production, test and development

** When access is missing

If access is not available, fall back in this order:
1. a walkthrough with the technical owner;
2. secondary artifacts (Dockerfile, CI/CD configuration);
3. observation of monitoring, APM, logs;
4. black-box inference, only as a last resort, marked =[DA VALIDARE]=.

* Workflow 5: the enterprise view

/When: once at least the main components are documented, to get the aggregate view./

The enterprise view is Part I of the master document. It has two files, both at the project root (not inside =.blueprint/=):
- =enterprise/context.org=: aggregate C4 level 1
- =enterprise/dependencies.org=: the dependency map

** Generate the C4 container diagram (Part II)

#+begin_src
M-x blueprint-generate-c4  (or: C-c b C)
#+end_src

Writes =c4.puml= at the project root, with every component as a Container and its dependencies as =Rel= relations, ready for PlantUML.

** Generate the enterprise C4 diagram (Part I)

#+begin_src
M-x blueprint-generate-enterprise-c4  (or: C-c b V)
#+end_src

Updates =enterprise/context.org= with a C4 level 1 diagram: a =System(...)= for each component and a =Rel(...)= for each =#+BLUEPRINT_DEPENDS:=. Unlike the container diagram (Part II), there are no =Container= elements here, only =System=.

The command only touches the area between the markers =' @@blueprint-enterprise-start@@= and =' @@blueprint-enterprise-end@@= inside the PlantUML block, exactly as =blueprint-sync= preserves what is written by hand in =master.org=. Everything beyond the components is written by hand, outside those markers:
- external systems as =System_Ext(...)=;
- users as =Person(...)=;
- relations to the outside (for example =Rel(user, system, "...")=).

If =enterprise/context.org= does not exist yet (a project initialized before this feature, or a file written by hand without the markers), the command reports an error instead of overwriting: regenerate the file from the updated =enterprise-context.org= template.

Then open =enterprise/dependencies.org= and fill in:
- the dependency matrix (an N×N table with IN/OUT/BI/--);
- the main cross-system flows (a sequence diagram for each relevant flow).

* Workflow 6: NFR, constraints and risks

/When: during and after the work on each component; risks come up naturally./

The NFR files cover the whole project (not one component) and live in =nfr/=. Each component's =arc42.org= also has a =* Risks= section for the risks specific to it, which points to the project-wide register.

** NFR files

| File                    | Content                                              |
|-------------------------+------------------------------------------------------|
| =quality-scenarios.org= | Quality scenarios (performance, reliability, ...)    |
| =constraints.org=       | Technical, organizational and regulatory constraints |
| =risks.org=             | The project-wide risk register                       |

** Quality scenarios

Each scenario follows the structure attribute, context, stimulus, expected response, measure, priority. Add them by hand or with =blueprint-nfr-add-quality-scenario= (=C-c b p=). For each scenario:

- quality attribute: performance, security, reliability, maintainability, scalability;
- stimulus: what triggers the scenario (for example "1000 concurrent requests");
- expected response: the correct behavior of the system;
- measure: a quantifiable criterion (for example "p95 latency < 200 ms").

Fill in the SLA table (uptime, RTO, RPO, p95 latency) for every critical service.

** Constraints

Three categories (=C-c b c= adds one):
- technical, for example "must run on JVM 11", "max 4 GB RAM per container";
- organizational, for example "the team in charge is two people", "no root access in production";
- regulatory, for example GDPR, PCI-DSS, SOC 2, with their compliance status.

** Risk register

Risk patterns can be detected automatically:

#+begin_src
M-x blueprint-suggest-risks-all  (or: C-c b s)
#+end_src

Detects patterns such as "no backup", "single point of failure", "hardcoded credentials", "no monitoring", "deprecated library", "isolated component". The results are moved into the register by hand, with an assessment of probability and impact.

Risks not detected automatically go into =risks.org= by hand, or with =blueprint-nfr-add-risk= (=C-c b t=): ID (R-NNN), description, components involved, probability, impact, level, mitigation, owner.

* Workflow 7: glossary and references

/When: continuously, for the whole project./

** Add a term to the glossary

#+begin_src
M-x blueprint-glossary-add  (or: C-c b y)
Term: SLA
Definition: Service Level Agreement, the contractual agreement on service levels
Source: client-contract-2024
#+end_src

The term goes into =glossary.org= as a level-2 heading at the end of the chosen section, in the template's own format: the definition and a =/Fonte: client-contract-2024/= line. The command asks for the section (domain terms by default, then technical terms with a specific use, then acronyms and abbreviations). Entries written by older versions (level 1 with a =:PROPERTIES:= drawer at the end of the file) stay valid: =blueprint-glossary-lookup= finds both.

** Look up a term

#+begin_src
M-x blueprint-glossary-lookup
#+end_src

It has no key in the Transient menu, only =M-x=.

** Add a source

#+begin_src
M-x blueprint-reference-add  (or: C-c b z)
Title: Interview with Jane Doe (lead developer)
Type: interview
Notes: Walkthrough of the order architecture, 2026-03-10
#+end_src

=Type: interview= files the source as a row of the interviews table; any other type (=document=, =codebase=, =monitoring=, =ticket=) goes into the documents table, where the type becomes the value of the "Tipo" column. The ID (=I-NN= or =D-NN=) is assigned automatically.

** Principle: full traceability

Every statement that does not come straight from the code needs an explicit source. Use =[FONTE: X]= in the text, or the references for formal traceability.

* Workflow 8: architecture decision records

/When: every time a significant architectural decision is taken or discovered./

ADRs record the decisions, their context and their consequences. They serve both for the client's decisions (found in the code) and for the decisions of the assessment itself.

** Add an ADR

#+begin_src
M-x blueprint-adr-new  (or: C-c b N)
ADR title: PostgreSQL as the primary database
#+end_src

Adds to =.blueprint/adr.org= a new level-1 heading with a sequential number:

#+begin_example
* ADR 0001: PostgreSQL as the primary database
:PROPERTIES:
:STATUS:   proposed
:DATE:     2026-03-05
:END:

** Contesto

Situation that led to this decision.

** Decisione

The decision taken and the alternatives considered.

** Conseguenze

Positive, negative and neutral consequences.
#+end_example

** ADR lifecycle

The states are =proposed=, then =accepted= (or =deprecated= / =superseded=). Update =:STATUS:= by hand after validating with the client.

** List the ADRs

#+begin_src
M-x blueprint-adr-list  (or: C-c b n)
#+end_src

Opens a =*Blueprint ADRs*= buffer with the title and state of every ADR. =RET= on an ADR opens =adr.org= at its heading.

* Workflow 9: monitoring the health of the assessment

/When: regularly, to see how much work is left and where to focus./

** Health score

#+begin_src
M-x blueprint-health-score
#+end_src

It has no key in the menu: the score also appears at the top of the dashboard (=C-c b B=) and in the pre-delivery check (=C-c b d=), and =C-c b H= draws it as an SVG gauge.

It returns a score from 0 to 100 computed on the text of the document exactly: =master.org= and every file it includes with =#+INCLUDE:=, nested includes too (an included file that includes others), with paths resolved relative to the including file. So Part 0 (the text of =master.org=), the glossary, Part I (=enterprise/=), the component documents, Part V (=nfr/=) and the references all count; files that =master.org= does not include (notes, knowledge base, questions, interviews) do not, and neither does a component document not yet synchronized. Every unresolved marker adds penalty points according to its weight:

| Marker             | Weight |
|--------------------+--------|
| =QUESTION=         |      3 |
| =TBD=              |      2 |
| =FIXME=            |      4 |
| =[DA VALIDARE]=    |      1 |
| =[DA REVISIONARE]= |      1 |
| =[FINDING]=        |      0 |

The sum P of the weights is compared with the size of the same files, so the score does not drop just because the document grows. With W the number of words of the exported text (same exclusions as the markers) and N the variable =blueprint-health-words-per-point= (100 by default):

#+begin_example
U     = W / N
score = round(100 * U / (U + P))
#+end_example

The score is 50 with one penalty point every N words. With P = 0 it is 100, even on an empty project; with P > 0 and no words it is 0. Doubling the document with the same proportion of markers leaves the score unchanged. Run with =M-x=, the command also shows P and W.

A score of 100 means every marker has been resolved. A low score does not mean "poor documentation" but "work still to do".

The same scope applies to every count in the package: dashboard, pre-delivery check, lint, risks, the lists of =[FINDING]= and =[DA VALIDARE]=. In the included files, markers only count in the exported text: =:noexport:= subtrees (or those with a tag from =#+EXCLUDE_TAGS:=) and =COMMENT= subtrees, src/example/export/comment blocks, comment lines and =verbatim=/~code~ text are excluded. =#+INCLUDE:= lines inside a non-exported subtree or a comment are not followed; a file included as a block (=#+INCLUDE: "x.org" src org=) does not count, because in the document it appears as code.

Known limits: a file included only in part (=:lines=, =file.org::*Heading=) counts in full; a file included twice counts once; =#+EXCLUDE_TAGS:= only applies to the file that declares it, while the export applies the one of =master.org= (and of the included files) to the whole document, and =#+SELECT_TAGS:= is not handled; =:minlevel= does not change the text and has no effect on the counts. Without =master.org= the document is not assembled yet, and the counts use the documents of every component, as =blueprint-sync= would include them.

** Lint

#+begin_src
M-x blueprint-lint  (or: C-c b L)
#+end_src

Checks:
- mandatory sections missing in =arc42.org= (only there: the other files do not have the arc42 headings);
- dependencies on components that do not exist (dangling dependencies), and in-scope components that depend on out-of-scope ones;
- in every file of the document (=master.org= and the included files, components or not): too many =QUESTION=/=TBD=/=FIXME= (above =blueprint-lint-marker-threshold=) and files with no content;
- =#+INCLUDE:= lines pointing to files that do not exist.

Warnings about a component file other than =arc42.org= read =component/functional.org: ...=; those about other files use the path relative to the root (=nfr/risks.org: ...=). =blueprint-ci-lint=, =blueprint-ci-validate= and the pre-delivery check use the same lint.

** Dashboard

#+begin_src
M-x blueprint-dashboard  (or: C-c b B)
#+end_src

One row per component, in alphabetical order, then one row for every other file of the document in the order =master.org= includes it (=master.org= itself, glossary, =enterprise/*=, =nfr/*=, references), identified by its path relative to the root. Every file of the document is on exactly one row, so the rows together make up the document's health score. The first line of the buffer holds the column titles; the header line at the top shows the document's health score, how many components and other files there are, and the active filters.

| Column             | Content                                                                      |
|--------------------+------------------------------------------------------------------------------|
| Name               | Component id, or path of the file                                            |
| Owner/Tech/Scope   | =#+BLUEPRINT_OWNER=, =#+BLUEPRINT_TECH=, =#+BLUEPRINT_STATUS= of =arc42.org= |
| QUESTION/TBD/FIXME | Technical markers                                                            |
| DA VAL             | =[DA VALIDARE]=                                                              |
| DA REV             | =[DA REVISIONARE]=                                                           |
| FINDING            | =[FINDING]= (weight 0, information only)                                     |
| Penalty            | Penalty points, with the health score weights                                |
| Health             | Score of the row alone (=-= for a component outside the document)            |
| Status             | OK, IN-PROGRESS, NEEDS-WORK, FIXME, or NOT-INCLUDED                          |

For a component, only its documents included in =master.org= count; a component none of whose documents is included is NOT-INCLUDED (synchronize it with =C-c b S=). Focus mode (=F=) keeps the rows with penalty points and the NOT-INCLUDED components, so a row with only =[FINDING]= does not appear. ~RET~ opens the file of the row; for a component it asks which document. =g= recomputes, =O= filters the out-of-scope components, =G= generates the colored SVG graph (=blueprint-dashboard-svg=).

The same numbers drive the colors of the graph: =C-c b h= (=blueprint-dashboard-svg=) draws the components and their dependencies, colored by score: red below 50 (the warning threshold of =blueprint-ci-validate=), yellow below 80 (the default of =blueprint-delivery-score-threshold=), green otherwise, grey when =master.org= includes none of the component's documents. It needs Graphviz (=dot=). The dependency graph on =C-c b G= (=blueprint-dependency-graph=) uses =blueprint-graph-backend=: with the default =plantuml= it writes the =.puml= source without colors, with =graphviz= the same colored SVG. =blueprint-daily= (=C-c b .=) offers the components and the other files of the document that have penalty points, most first; for a component it then asks which document to open and preselects the one with the most penalty.

** Automatic risk detection

#+begin_src
M-x blueprint-suggest-risks-all  (or: C-c b s)
#+end_src

Looks for risk patterns (no backup, single point of failure, hardcoded values, deprecated technologies, no monitoring, manual processes) in the exported text of the document: for each component in all its documents included in =master.org=, then in every other file of the document. It also reports isolated components (no dependencies in or out) and immature documentation (more than 8 =QUESTION=/=TBD=/=FIXME= in the files of a row). =M-x blueprint-suggest-risks= does the same for a single component.

/When: regularly, and before every intermediate delivery./

#+begin_src
M-x blueprint-sync  (or: C-c b S)
#+end_src

Updates the three self-managed sections of =master.org= with the current component files:

| Marker pair                               | Synchronized section           |
|-------------------------------------------+--------------------------------|

* Workflow 11: export and delivery

/When: for intermediate reviews with the client and for the final delivery./

** Export to ODT

#+begin_src
M-x blueprint-export-odt  (or: C-c b O)
#+end_src

Uses =org-odt-export-to-odt= (Org's native export, no external dependency). It honors =#+ODT_STYLES_FILE:= set in =master.org=: that is how a company template (the client's header and styles) is applied, which PDF via LaTeX has no equivalent for. The default backend stays =pdf= (a package value, shared by every project and user); to make =odt= your personal default, set =blueprint-export-backend= in your own configuration (=:custom= in =use-package blueprint=), not in the package.

Two export choices are configurable. =blueprint-export-double-hyphen= decides what ="--"= becomes in ODT, HTML and LaTeX: =except-words= (default) turns it into an en dash except between two letters or digits, so a name like =acme--portal= stays intact even outside verbatim; =always= always turns it into an en dash, like Org; =never= always leaves two hyphens. ="---"= is an em dash in every case. =blueprint-export-odt-images-as-char= (on by default) anchors captioned figures as characters in ODT, centered: a figure that does not fit on the page moves to the next one instead of covering the previous one.

** Check a company =#+ODT_STYLES_FILE:= template

A "raw" company =.ott= template (written in LibreOffice Writer, not derived from an Org export) replaces =styles.xml= entirely, including the internal styles Org needs (=OrgDisplayImage=, =OrgTable*=, =OrgCode=, =OrgBulletedList=/=OrgNumberedList= and so on). The document comes out "almost right", with no error and no warning, but paragraph images (every diagram included through =#+begin_src plantuml :file x.svg=) overlap the content that follows instead of reserving their vertical space.

#+begin_src
M-x blueprint-check-odt-styles  (or: C-c b k)
#+end_src

Exports =master.org= to ODT and compares the styles the document references with those defined in the custom template, reporting only the ones Org normally provides itself (from its bundled =OrgOdtStyles.xml=) and that the template silently dropped. It needs =unzip= to inspect the generated =.odt=. Run it before delivering a document with a new or modified company template, not only the first time: a template update can bring the same problem back.

** Page breaks

To start every component on a new page in the parts managed by =blueprint-sync= (II, III and IV), add to =master.org=:

#+begin_src org
,#+BLUEPRINT_PAGE_BREAK: components
#+end_src

At the next =blueprint-sync=, two lines appear before every component heading except the first of each part:

#+begin_src org
,#+ODT: <text:p text:style-name="PageBreak"/>
,#+LATEX: \clearpage
#+end_src

Each exporter uses its own line and ignores the other: ODT starts a new page through the =PageBreak= paragraph style, PDF via LaTeX through =\clearpage=. The first component of each part stays on the page of the part's title. Removing the keyword, the next sync removes the breaks too. A value other than =components= is ignored with a message.

For a break anywhere else, outside the synchronized sections:

#+begin_src
M-x blueprint-insert-page-break
#+end_src

The =PageBreak= style must exist in the =#+ODT_STYLES_FILE:= template (a paragraph with =fo:break-before="page"=): if it is missing, LibreOffice ignores the break without warning. =blueprint-check-odt-styles= reports it together with Org's internal styles.

** Export to Word (.docx)

#+begin_src
M-x blueprint-export-docx
#+end_src

Pipeline: Org mode, then Pandoc, then =.docx=. It needs the =ox-pandoc= package.

If the client has a company Word template (header, footer, styles, logo), save it as =.blueprint/templates/reference.docx= before exporting: Blueprint uses it as Pandoc's reference document.

** Export to PDF

#+begin_src
M-x blueprint-export-pdf  (or: C-c b P)
#+end_src

Pipeline: Org mode, then LaTeX, then PDF (through Org's exporter). It does not apply =#+ODT_STYLES_FILE:= or a Word template: for a company template, prefer ODT or DOCX.

** Choose the format at export time

#+begin_src
M-x blueprint-export-dispatch  (or: C-c b v)
#+end_src

Opens =master.org= and hands over to Org's standard menu (=org-export-dispatch=): any backend Org knows (ODT, PDF, HTML, ASCII, ...) and any per-file option Org already supports (=#+ODT_STYLES_FILE:=, =#+LATEX_CLASS:= and so on) are chosen there, instead of being fixed in advance by =blueprint-export-backend=. =M-x blueprint-export= (=C-c b E=) stays the shortcut that always uses the default backend.

** Headless CI

For CI/CD or automated workflows:

#+begin_src bash
  # Lint: exit 0=ok, 1=warning
  emacs -Q --batch -l blueprint.el -f blueprint-ci-lint

  # Validate: exit 0=ok, 1=warn, 2=error
  emacs -Q --batch -l blueprint.el -f blueprint-ci-validate

  # Export: exit 0=ok, 2=error
  emacs -Q --batch -l blueprint.el -f blueprint-ci-export
#+end_src

Lint and health score cover the whole document (=master.org= and the included files), so a warning in Part 0, I or V changes the exit code just like a warning in a component.

* Workflow 12: review and approval

/When: before every delivery to the client and before the final one./

** Pre-delivery checklist

=M-x blueprint-pre-delivery-check= (=C-c b d=) checks the health score, the remaining =[DA VALIDARE]= and =[DA REVISIONARE]=, the lint warnings and whether =master.org= is synchronized. All the counts concern the document only, that is =master.org= and the files it includes (see the health score): markers in notes, knowledge bases or other =.org= files of the project do not count. The number of =[FINDING]= appears with the =[INFO]= label, for information only: a finding is a result to deliver, so it raises no warning and does not change the outcome.

Before delivering the document to the client, check by hand:

- [ ] every =[DA VALIDARE]= has been verified or removed
- [ ] every =[DA REVISIONARE]= has been reviewed
- [ ] the glossary covers every technical and domain term used in the document
- [ ] the references are complete and can be checked
- [ ] the PlantUML diagrams are rendered and readable
- [ ] Part 0 describes the scope and the sources actually used
- [ ] findings are written as observations, not as criticism
- [ ] the health score is at an acceptable level (recommended: above 80)
- [ ] the lint reports no blocking errors
- [ ] the document has been exported in the agreed format and checked by eye
- [ ] the client's owner has approved the version

** Approval cycle

For every section the client approves, update the marker:

#+begin_example
[APPROVATO 2026-03-15]
#+end_example

The approval date keeps track of validity over time: if the system changes after that date, the section goes back to =[DA VALIDARE]=.

* Workflow 13: project tools

/When: day-to-day project management: metrics over time, question triage, history, comparisons between versions./

** Metrics over time

Every =blueprint-sync= (=C-c b S=) records a line in =.blueprint/metrics-history.org= with the document's score, penalty points, words and marker counts (=blueprint-history-on-sync=, on by default). A line with the same values as the previous one is not added. The file lives in the data directory and is not included in =master.org=: it is never counted.

=M-x blueprint-metrics-history= (=C-c b x=) draws the trend of the score as an SVG and shows it; with no records it just says so.

** Milestones in the dashboard

If the project root has a =CRONOPROGRAMMA.org= or =TODO.org= (=blueprint-milestone-files=), the status line of the dashboard (=C-c b B=) adds the next open milestone (the first heading with the =TODO= keyword in file order, with its =:DEADLINE:= as the date, if any) and the number of open =TODO= items. No new format: it reuses Org's TODO/DONE headings. A malformed file does not break the dashboard: the status line simply has no milestone. The milestone comes after the project version, and its title is cut at =blueprint-dashboard-milestone-width= characters (40; nil not to cut it), with the full title in the tooltip.

** Questions: tags, answers and filters

=blueprint-add-question= (=C-c b Q=) also asks for an optional tag, which ends up on the line as =[TAG: tag]=. A question is closed with =M-x blueprint-answer-question=: the line becomes =- ANSWERED [date] text [FONTE: source]=. It stops counting in the health score, dashboard and lint, but stays in the file with the source of the answer, following the method's =[FONTE: X]= convention. The question list (=C-c b q=) shows Tag and State and filters by tag (=t=) and by state (=s=); the open entries of the list match the QUESTION column of the dashboard. Lines written by earlier versions stay valid and open.

** Triage in org-agenda

=M-x blueprint-agenda= (=C-c b U=) regenerates =.blueprint/agenda.org= and opens the Org agenda on that file: every QUESTION and FIXME of the document becomes a TODO entry with a link to where it came from. Deadlines (=DEADLINE=), dates (=SCHEDULED=) and states (TODO/DONE) set by hand are preserved across refreshes. With =blueprint-agenda-add-to-org-agenda= the file also joins the user's =org-agenda-files=.

** Project history

=M-x blueprint-changelog-generate= (=C-c b J=) regenerates =CHANGELOG.org= from the git commit messages (newest first, grouped by date; with =C-u= it can be limited to =SINCE..HEAD=) and from the ADRs with =:STATUS: accepted=. The file is derived: if it already exists, the command asks before overwriting it.

** Comparing versions of a component

=M-x blueprint-component-diff= shows the =git diff= of the component's directory against the last commit (=HEAD=, staged changes included), headed by a semantic summary: files touched, headings changed, markers added or removed, questions resolved. With a prefix argument it compares against a revision (a tag or a commit). Files never added to git (untracked) do not appear. In the component list (=C-c b l=), =d= does the same for the component at point. The command is read-only.

** Graph preview

=M-x blueprint-preview= opens the dependency graph colored by health in a side window and turns on =blueprint-preview-mode=: every time an Org file of the project is saved, the graph is regenerated (after =blueprint-preview-delay= seconds) and the buffer refreshes. It needs Graphviz (=dot=); without it, it says so once. The mode is off by default and never opens windows on its own.

* Native Org features supported

For the layout and apparatus of the final document, Org's built-in tools (=ox=, =ox-odt=, =ox-latex=, =oc=) are preferred over new constructs inside Blueprint. This section states which native features Blueprint supports and guarantees along its whole chain (sync, =#+INCLUDE= with =:minlevel=, lint, health, ODT/PDF/DOCX export, ODT style check): for each one, the syntax, the behavior per backend, what Blueprint checks and the known limits.

** Footnotes

- *Syntax*: =[fn:: footnote text]= inline, or =[fn:name]= in the text with the definition =[fn:name]= (or a paragraph starting with =[fn:name]=) further down the file.
- *Behavior per backend*: in ODT every footnote becomes a =<text:note>= with citation and body (style =Footnote=); in PDF/LaTeX a =\footnote=; in DOCX through Pandoc. Numbering is unique across the assembled document: footnotes in a file included with =#+INCLUDE= continue the master's numbering, they do not restart (checked by the test =blueprint-test-export/footnotes-reach-content-xml=). They also work inside table cells.
- *What Blueprint checks*: footnotes are exported text, so they enter every count (health score, markers, lint, lists) like any paragraph; =blueprint-check-odt-styles= reports the =Footnote= style if a company =#+ODT_STYLES_FILE:= template does not define it (it is one of the baseline styles of Org's =OrgOdtStyles.xml=).
- *Limits*: the definition of a named footnote must be in the same file as its reference (Org resolves footnotes per buffer, not across =#+INCLUDE=).

** Citations (oc)

- *Syntax*: =[cite:@key]= with =#+bibliography: file.bib= and =#+print_bibliography:=, using the default =basic= processor (no external package needed).
- *Behavior per backend*: ODT, PDF and HTML with the =basic= processor produce the essential apparatus (author-year or numeric, without CSL). Blueprint changes nothing: citations are exported text and follow Org's standard path.
- *What Blueprint checks*: nothing specific; the counts treat them as text.
- *Limits*: advanced CSL styles need =citeproc-el= (outside Blueprint's scope).

** Page breaks

- *Syntax*: the Blueprint keyword =#+BLUEPRINT_PAGE_BREAK: components= in =master.org= (automatic breaks between synchronized components, see workflow 11) or =M-x blueprint-insert-page-break= for a manual break.
- *Behavior per backend*: two native keyword lines, =#+ODT:= (a paragraph with the =PageBreak= style) and =#+LATEX: \clearpage=; each backend uses its own and ignores the other.
- *What Blueprint checks*: the =PageBreak= style is in the list of extra styles of =blueprint-check-odt-styles=, reported if a company template does not define it.
- *Limits*: an Org macro cannot be used here (it would expand inside a paragraph, producing a nested =<text:p>= in ODT).

** Export keywords per backend

- *Syntax*: =#+ODT:=, =#+LATEX:=, =#+HTML:=, one line per backend, handled only by the matching exporter.
- *Behavior per backend*: these keywords are how Blueprint itself writes page breaks (above), and how raw output can be added (for example =#+LATEX: \newpage=). The =#+begin_export odt= / =latex= / =html= blocks are the block equivalent.
- *What Blueprint checks*: nothing specific: the content of the keywords counts as exported text.
- *Limits*: none beyond Org's.

** Size of images and wide diagrams

- *Syntax*: =#+ATTR_ODT: :width 25cm= (or =:height=) above the paragraph or block that produces the image; =#+ATTR_LATEX:= / =#+ATTR_HTML:= for the other backends.
- *Behavior per backend*: ODT applies the explicit size instead of computing one (for SVGs, Blueprint's advice on =org-odt--image-size= measures width/height or the viewBox, and stops when =:width=/=:height= are given, see workflow 11); LaTeX and HTML follow their own attributes.
- *What Blueprint checks*: the test =odt-svg-user-width-honoured= covers the explicit case.
- *Limits*: very wide diagrams (C4 container, ER) at full page width still have small text: the alternatives are a landscape page (a company template with a landscape page style) or a vertical layout in the PlantUML sources.

* Workflow 14: updating an existing project

/When: a project created with an earlier version of Blueprint, even one before 0.1.0./

Blueprint reads every format it has ever written: an old project opens and can be worked on immediately, without migrating anything. A migration is always available but optional, to run when there is time: no deadline should depend on updating the documentation tool.

** Project version

=.blueprint/blueprint-version.org= records the Blueprint version that created or last updated the project, and the migrations applied. =blueprint-init= writes it; for projects that lack it, the version is inferred from the file layout (for example "0.2.0 (until 2026-03)" for a project with one file per ADR). The file is not included in =master.org=. Every applied migration writes it too; writing it is not a migration, so a project in the current format without the file has no migrations available and says so with =v= in the plan.

The status line of the dashboard (=C-c b B=) shows the version, declared or inferred, the number of migrations available, and the project and user templates older than the system ones (=blueprint-dashboard-show-version= hides it). =u= in the dashboard opens the plan.

** The migration plan

#+begin_src
M-x blueprint-project-upgrade  (or: C-c b ^)
#+end_src

Opens the =*Blueprint Upgrade*= buffer, with a row for each available step and for each template to review. Nothing changes until you ask:

- =x= applies the step at point (or updates the template at point), after confirmation;
- =X= applies every step, then offers to update the unmodified templates;
- =d= (or =RET=) shows the files of a step or the diff of a template;
- =v= writes =blueprint-version.org= (the inferred version while steps remain, otherwise the package's);
- =g= recomputes the plan.

The steps, from the oldest format:

| Step                     | Starting format                                                  |
|--------------------------+------------------------------------------------------------------|
| =component-arc42-layout= | component with =* Component= and level-2 sections (< 0.1.0)      |
| =component-dir-ids=      | component directory named as typed, not by its id                |
| =project-files=          | project files missing (Parts I and V, glossary, ...)             |
| =master-sync-sections=   | master.org without the synchronized sections of Parts III and IV |
| =component-documents=    | components without =functional.org= / =infrastructure.org=       |
| =adr-single-file=        | one file per ADR in =.blueprint/adr/= (until 2026-03)            |
| =orphan-glossary=        | terms written in =.blueprint/glossary.org= (until 2026-09)       |
| =orphan-references=      | references written in =.blueprint/references.org=                |
| =references-table-rows=  | references as headings with a =:TYPE:= drawer                    |
| =data-directory=         | =.blueprint= when =blueprint-directory-name= is something else   |
| =glossary-sections=      | terms as level-1 headings with a =:SOURCE:= drawer               |
| =lifecycle-keyword=      | components without =#+BLUEPRINT_LIFECYCLE:= (becomes =active=)   |
| =agenda-ids=             | =agenda.org= from 0.3.0 (IDs on absolute paths)                  |

The files created by =project-files= and =component-documents= start empty: the lint reports them until they are filled in, and the next =blueprint-sync= includes them in the document.

** Safety

Before touching a file, every migration copies it to =_archive/migration-YYYYMMDD-HHMMSS/= with the same relative path, together with a =report.org= of the steps applied (=blueprint-upgrade-backup=, =blueprint-upgrade-backup-directory=). In a git repository with uncommitted changes the command warns and continues (=blueprint-upgrade-git-check=: =warn=, =refuse= to stop, nil not to check); renames and deletions go through =git mv= and =git rm= when the files are tracked.

** Project and user templates

The copies in =.blueprint/templates/= and in =~/.config/blueprint/templates/= (=blueprint-template-status-scopes=) are compared with every released version of the system templates:

- /previous version/: identical to an old version, never modified. =x= replaces it with the current one, keeping the old one in a =backup-YYYYMMDD-HHMMSS= directory next to it;
- /customized/: different from every released version. It is never replaced: =d= shows the diff against the current template, and aligning it is done by hand.

** CI

=blueprint-ci-validate= reports the version and the available migrations; the exit code only changes if you ask for it with =blueprint-ci-pending-migrations= (=ignore= by default, =warn= exits with 1, =error= with 2). The JSON report (=blueprint-ci-export-json=) has the same information under the =blueprint= key.
