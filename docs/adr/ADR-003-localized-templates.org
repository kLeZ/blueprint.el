#+TITLE: ADR-003: Localized templates and generated text
#+DATE: 2026-11-16
#+STATUS: accepted

* Context

Blueprint is Italian throughout, and the language is not only in the templates:

- *Templates*: every file under =templates/= (headings, the =:noexport:= guides, the examples, =master.org= with its parts) is written in Italian.
- *Headings the code looks up by name*: =blueprint-functional.el= finds "Aree funzionali", "Entità di dominio" and "Punti di integrazione"; =blueprint-runtime.el= finds "Processi di business"; =blueprint-lint.el= lists the arc42 sections it expects. A project whose headings are translated breaks the commands that add functional areas, features, entities, integration points and business processes.
- *Generated text*: the commands insert Italian prose (for example the overview line of a runtime flow in =blueprint-runtime.el=), and some messages and file headers too (PLAN 9.37).
- *Markers*: =[DA VALIDARE]=, =[DA REVISIONARE]=, =[APPROVATO YYYY-MM-DD]= are Italian words that the health score and the linter recognize.

The documentation is moving to English (README, USAGE, the method in =docs/method/=) so the package can be used outside Italy. Today an English-speaking user can read about Blueprint but cannot produce an English document with it, and the demo in =examples/demo/= has to stay Italian for its own commands to work on it.

* Decision

D1, D2 and D3 were taken by the user on 2026-11-16; D4 and the rename of the JSON report keys (see Compatibility) were confirmed by the user the same day, after the implementation.  The user rejected the string catalog of the first implementation (=blueprint-l10n.el=, one alist of all translations): how translations are stored is being redesigned, see PLAN.org 11.7.

** D1: the language belongs to the project

The document language is recorded per project, in =.blueprint/blueprint-version.org=, as =#+BLUEPRINT_LANGUAGE: en= (an ISO 639-1 code). =blueprint-init= writes it from the defcustom =blueprint-default-language=, whose default is ="en"=: the public of the package is no longer only Italian, and an Italian user sets the option once. A project without the keyword (every project created before this change, with or without a version file) is Italian: that is what it was written in, so it keeps working with no migration (ADR-002). Changing the defcustom never changes an existing project.

** D2: sections are found by a property, with the Italian titles as fallback

Every heading the code looks up carries a property in the templates:

#+begin_src org
  ,* Entità di dominio
  :PROPERTIES:
  :BLUEPRINT_SECTION: domain-entities
  :END:
#+end_src

The code finds a section by its =BLUEPRINT_SECTION= first; when no heading has it, by its title: the one the templates of the project language give it, or the one Blueprint 0.4.x wrote.  The 0.4.x titles are a frozen list in the code (option C, user, 2026-11-16): documents without the property are only those written by 0.4.x and earlier, a closed set, so the list never grows.  Titles of other languages are not used: a match would be a coincidence. Headings become free text: a user can rename or translate them. Projects created before keep working through the title fallback (the lint also accepts a title that starts with the expected one, as its old prefix match did); an optional upgrade step adds the property to the headings it recognizes.  Property drawers are not exported, so they count neither as content for the lint nor as words for the health score. When a command has to create a missing section, it writes the heading in the project language, with the property.

Preferred to the existing =<<{{ID}}-...>>= anchors (alternative B as first written) by the user: one uniform mechanism also for the files that have no component id (glossary, references, NFR), at the cost of a property drawer under each heading in the source. Property drawers are not exported by default (=org-export-with-properties= is nil).

** D3: one canonical set of markers, in English

The methodology markers become English for every language: =[TO VALIDATE]=, =[TO REVIEW]=, =[APPROVED YYYY-MM-DD]=, =[SOURCE: X]=; =[FINDING]=, =QUESTION=, =ANSWERED=, =TBD=, =FIXME= and =[TAG: x]= are already English. The commands and the templates of every language write the English markers. The Italian ones (=[DA VALIDARE]=, =[DA REVISIONARE]=, =[APPROVATO YYYY-MM-DD]=, =[FONTE: X]=) stay recognized as legacy everywhere they are read today (health score, lint, lists, pre-delivery check, questions, agenda), and an optional upgrade step rewrites them. An Italian document therefore carries English markers from now on: a deliberate choice, since the markers are syntax of the tool, not prose of the document.

** D5: translations are files, one set per language

User decision (2026-11-16), after rejecting a first implementation that kept every translation in one alist of a Lisp file.  A language is a folder: =templates/<lang>/= with the document templates, =snippets/= (the skeletons the commands insert, one file each, placeholders such as ={{NAME}}=) and =strings.org= (the short texts, one level-1 heading per key).  Every file goes through the three tiers of the template lookup; a key missing in a =strings.org= is looked up in the next tier and finally in English.  The available languages are the folders found in the package and in the user directory.  The title of a section is the one its template gives the heading with the property.  The code that reads all this is in one file, =blueprint-l10n.el=, which holds no translated text.  Considered and rejected: gettext (no runtime in Emacs Lisp, and made for interface messages, while what is translated here is Org content) and Org's own =org-export-dictionary= model (one alist with every language, the model rejected).

** D4: what is localized and what is not

- Localized, in the project language: the templates (=templates/<lang>/=), the headings and the prose the commands insert, the headers of the files Blueprint writes in the project (=agenda.org=, =metrics-history.org=, the README of a migration backup), the default lists offered for completion (quality attributes, constraint types).
- Not localized: the user interface (prompts, messages, buffer headers) is English, like Emacs itself; the Italian strings that leaked into it are translated, not put in the catalog.

Templates: =templates/it/= and =templates/en/= in the package, =~/.config/blueprint/templates/<lang>/= for the user. The flat =~/.config/blueprint/templates/= of earlier versions is still read, as Italian, after the language folder. The project folder =.blueprint/templates/= stays flat: a project has one language.

* Consequences

** Positive
- An English-speaking user gets an English document, with the same commands.
- A new language is a folder of files, in the package or in the user directory; no change to the code.
- Headings can be renamed without breaking the commands.

** Negative
- Every heading the code looks up gets a property drawer in the source.
- Two sets of templates to keep aligned; a change to one has to be made in the other.
- Italian documents created from now on mix Italian prose and English markers.

** Risks
- A custom user or project template without the properties still works only through the title fallback, that is with the known titles.
- The template history (=blueprint-template-history.el=) changes key: entries are per language folder, and the Italian entries keep the hashes of the flat =templates/= of the past releases.

** Compatibility
- JSON report: the marker keys change to the English names (=to-validate=, =to-review=; they were =da-validare=, =da-revisionare=), with the same counts.  It is the only visible change for a CI that reads the report.  Confirmed by the user: nothing outside the repository reads the report.
- Checked on the demo project (a 0.4.x project): with this change and without migrating, =blueprint-ci-lint= gives the same output as 0.4.1 and =blueprint-ci-validate= adds only the line of the two optional migrations; after both migrations the output is the same as 0.4.1.
