#+TITLE: ADR-002: Project version, optional migrations and template status
#+DATE: 2026-11-02
#+STATUS: accepted

* Context

Two rules set by the user (2026-11-02), which also revise PLAN.org 10.8
("nessuna migrazione" meant "no forced migration", not "no migration"):

1. Blueprint must read every project format it ever wrote, without asking
   for a migration first: a user with a deadline must never be blocked by
   the tool.
2. A migration path must always exist, optional, run when the user decides.

Projects may come from any version, pre-0.1.0 included, so both rules
apply back to the initial commit. The dashboard must show the project's
Blueprint version and whether a migration is available, for the project
and for the user templates (=~/.config/blueprint/templates/=), so that the
work can be planned.

The version number alone does not identify a layout: "0.2.0" covers seven
months (2026-02-22 to 2026-10-15) and several incompatible layouts. The
projects do not record which version created them.

(space-separated) and escapes the duplicate check of

(2) PR #2 hashes root-relative paths: a 0.3.0 =agenda.org= loses its
DEADLINE/SCHEDULED/state at the first refresh.

Rows 3, 4 and 13 break rule 1 today and are fixed regardless of the
decisions below. Rows 2 and 12 need no migration (content, or already
compatible).

* Decision

** D1: the project records its version in =blueprint-version.org=

A small Org file in the data directory (=.blueprint/blueprint-version.org=),
never included in master.org.  User decision (2026-11-02): the name must
be unmistakable; a =project.org= could later be a functional document of
the project, which is documentation after all.

#+begin_src org
,#+TITLE: Versione Blueprint del progetto
,#+BLUEPRINT_VERSION: 0.3.0
,#+BLUEPRINT_MIGRATIONS: adr-single-file glossary-sections ...
#+end_src

Written by =blueprint-init= and by every applied migration, never
required: a project without it gets an /inferred/ version from its
layout (rows 1-14 are the detectors), shown as such.

** D2: a registry of migration steps and one optional command

Each step has an id, the version that introduced the format, a
/detector/ (pending or not, read-only) and an /apply/ function
(idempotent). =blueprint-project-upgrade= builds the plan from the
detectors, shows it in a buffer (step, files touched, what changes), and
applies the steps the user confirms, all or one by one, in version order.
Nothing runs on its own: commands keep reading the old formats.

** D3: backup before apply, git check configurable

Every file a step rewrites, moves or deletes is copied first to
=_archive/migration-YYYYMMDD-HHMMSS/= (=blueprint-init= already creates
=_archive/=), with the plan as a report.  User decision: both safeguards,
the backup always and, in a git working tree with uncommitted changes, a
warning that does not block (=blueprint-upgrade-git-check=: =warn=,
=refuse= or nil).  Renames go through =git mv= when the file is tracked,
as =blueprint-migrate-directory= does.

** D4: template status through the hashes of every released version

A table of the MD5 of every version of every system template, extracted
from git history and shipped with the package, classifies each project
or user template as /current/, /stale/ (identical to an older system
version: can be updated, with backup) or /customized/ (matches no
version: only the diff is shown, the user merges by hand).

** D5: dashboard, JSON report and CI signal

The dashboard summary line adds the version (declared or inferred), the
number of pending migrations and of templates to update; =u= in the
dashboard opens the upgrade plan.  The JSON report gets the same fields.
User decision: the effect on =blueprint-ci-validate= is configurable
(=blueprint-ci-pending-migrations=: =ignore= by default, =warn= exits 1,
=error= exits 2).

** D6: configurable behaviour (user decision 2026-11-02)

Choices on which users may reasonably disagree become defcustoms, with
the current behaviour as default:

| Defcustom                              | Values (default first)          | Choice it exposes                           |
|----------------------------------------+---------------------------------+---------------------------------------------|
| =blueprint-ci-pending-migrations=      | ignore, warn, error             | CI exit code with a migration available     |
| =blueprint-upgrade-git-check=          | warn, refuse, nil               | uncommitted changes before a migration      |
| =blueprint-upgrade-backup=             | t, nil                          | copy rewritten files to the archive         |
| =blueprint-upgrade-backup-directory=   | "_archive"                      | where the backups go (relative to the root) |
| =blueprint-template-status-scopes=     | (project user)                  | which template directories are checked      |
| =blueprint-dashboard-show-version=     | t, nil                          | version/migrations in the dashboard         |
| =blueprint-diff-default-base=          | head, index                     | component diff without a revision           |
| =blueprint-agenda-view=                | block, agenda, todo             | what =blueprint-agenda= opens               |
| =blueprint-glossary-source-position=   | after, before                   | /Fonte:/ line after or before a definition  |

Already configurable and kept: =blueprint-lint-lifecycle-checks=,
=blueprint-history-on-sync=, =blueprint-agenda-marker-types=,
=blueprint-agenda-add-to-org-agenda=, =blueprint-milestone-files=,
=blueprint-preview-delay=, =blueprint-ci-report-file=.

* Alternatives considered

Pugh matrix for D1, baseline = no record, detection only (C).

| Criterion                          | A: keyword in master.org | B: .blueprint/project.org | C: detection only |
|------------------------------------+--------------------------+---------------------------+-------------------|
| Works on projects without master   |                       -1 |                         0 |                 0 |
| Distinguishes 0.2.0 sub-layouts    |                       +1 |                        +1 |                 0 |
| Keeps the deliverable untouched    |                       -1 |                         0 |                 0 |
| Records applied migrations         |                       +1 |                        +1 |                 0 |
| Implementation cost                |                        0 |                         0 |                 0 |
| Total                              |                        0 |                        +2 |                 0 |

D2: one command per migration (no registry) was considered: simpler, but
the dashboard could not say "N pending" without duplicating every
detector, and the order between steps would be up to the user.

D3: requiring a clean git tree was considered: safe, but it blocks the
projects that are not under git and the user with uncommitted work, the
scenario rule 1 protects.

D4: comparing only with the current system template was considered: it
cannot tell a stale unmodified copy from a customized one, so it could
only show diffs and never offer a safe update.

* Consequences

** Positive
- Every layout since the initial commit stays readable; rows 3, 4, 13
  become readable again.
- One place lists what a project can migrate, with a backup per run.
- The dashboard tells which projects and user templates are behind.

** Negative
- One more file in the data directory.
- Every future format change needs its detector and its step (a check in
  the release procedure).

** Risks
- A detector that misreads a hand-edited file proposes a wrong step:
  mitigated by the plan buffer (nothing applies unseen) and the backup.

** Technical debt
- The template hash table must be regenerated at each release (a script
  over git history, run by the release procedure).
