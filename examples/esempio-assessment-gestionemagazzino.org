* Parte 0 — Premesse

** Obiettivo e perimetro

Il presente documento raccoglie i risultati dell'assessment architetturale
condotto sul sistema *GestioneMagazzino*, applicazione web PHP/MySQL in
produzione dal 2014 presso Logistica Nord S.r.l.

L'obiettivo è fornire al management una fotografia completa dello stato attuale
del sistema, identificare rischi tecnici e proporre un percorso di
modernizzazione incrementale.

*Perimetro dell'analisi:*
- Applicazione web PHP (Apache/MySQL su server Linux)
- 4 moduli funzionali principali
- 2 job schedulati (crontab)
- Infrastruttura di produzione e staging

*Esclusi dal perimetro:*
- Sistema di fatturazione elettronica (gestito da fornitore esterno)
- App mobile del magazziniere (progetto separato, non ancora in produzione)

** Metodo di lavoro

L'analisi segue una metodologia strutturata basata su Arc42, adattata per
scenari di reverse-engineering su sistemi legacy privi di documentazione
preesistente.

*Gerarchia delle fonti informative* (in ordine di affidabilità):
1. Codice sorgente (repository Git interno)
2. Test automatici (PHPUnit, parziali)
3. Log applicativi e di sistema
4. Monitoraggio (Munin, accesso limitato)
5. Interviste con il team di sviluppo (2 persone)
6. Documentazione esistente (README obsoleto del 2016)

*Convenzioni di marcatura:*
- Le informazioni riportate sono state verificate sul codice salvo diversa indicazione
- Dove indicato "[da intervista]", l'informazione proviene da colloquio con il team
- Le sezioni approvate dal committente riportano la data di approvazione

* Parte II — Architettura per componente

** GestioneMagazzino — Architettura applicativa

*** Introduzione e panoramica

GestioneMagazzino è un'applicazione web monolitica PHP sviluppata internamente
dal 2014. Segue un pattern MVC artigianale senza framework, con routing basato
su parametri GET (~?module=ordini&action=lista~).

L'applicazione è composta da 4 moduli funzionali:
1. *Catalogo Prodotti* — anagrafica articoli e gestione SKU
2. *Gestione Ordini* — ciclo di vita dell'ordine dall'ingresso all'evasione
3. *Monitoraggio Scorte* — giacenze in tempo reale e movimentazione
4. *Reportistica* — dashboard KPI e generazione report PDF/CSV

*** Vincoli

| Vincolo                      | Tipo           | Impatto                                     |
|------------------------------+----------------+---------------------------------------------|
| PHP 7.4 (EOL dicembre 2022)  | Tecnico        | Nessuna patch di sicurezza disponibile      |
| MySQL 5.7 (EOL ottobre 2023) | Tecnico        | Vulnerabilità note non corrette             |
| Nessun framework PHP         | Tecnico        | Codice custom per routing, auth, templating |
| Server fisico singolo        | Infrastruttura | Single point of failure                     |
| Team di 1 sviluppatore       | Organizzativo  | Bus factor = 1, nessun code review          |
| Budget IT limitato           | Organizzativo  | Modernizzazione solo incrementale           |

*** Strategia di soluzione

L'applicazione adotta un'architettura MVC artigianale con le seguenti scelte
progettuali (ricostruite dal codice):

| Aspetto               | Scelta attuale                   | Motivazione ricostruita            |
|-----------------------+----------------------------------+------------------------------------|
| Persistenza           | Query SQL dirette (mysqli)       | Semplicità, assenza di ORM         |
| Autenticazione        | Sessioni PHP + tabella ~users~   | Implementazione minimale           |
| Templating            | PHP inline (file .php con HTML)  | Nessuna separazione netta          |
| Routing               | ~index.php~ + parametri GET      | Pattern classico PHP pre-framework |
| Dipendenze esterne    | Inclusione manuale (no Composer) | Progetto nato prima di Composer    |
| Generazione documenti | TCPDF per PDF, fputcsv per CSV   | Librerie standalone                |

L'operatore accede alla lista ordini in coda, seleziona un ordine e avvia la

** Aree funzionali

*** Catalogo Prodotti

**** Gestione anagrafica prodotto

***** Scopo
Consente la creazione, modifica e disattivazione dei prodotti a catalogo.
Ogni prodotto è identificato univocamente da un codice SKU e contiene le
informazioni necessarie per la gestione logistica (peso, dimensioni, scorta
minima, fornitore).

***** Input

| Campo           | Tipo di dato | Vincoli                              | Sorgente  |
|-----------------+--------------+--------------------------------------+-----------|
| SKU             | Stringa      | Univoco, formato ~[A-Z]{2}-[0-9]{5}~ | Operatore |
| Nome prodotto   | Stringa      | Max 200 caratteri, obbligatorio      | Operatore |
| Descrizione     | Testo        | Opzionale, max 2000 caratteri        | Operatore |
| Categoria       | Enum         | Da tabella ~categorie~               | Operatore |
| Prezzo unitario | Decimale     | >= 0.01, 2 decimali                  | Operatore |
| Peso (kg)       | Decimale     | >= 0, 3 decimali                     | Operatore |
| Scorta minima   | Intero       | >= 0, default 10                     | Operatore |
| Fornitore       | FK           | Da tabella ~fornitori~               | Operatore |
| Attivo          | Booleano     | Default true                         | Sistema   |

***** Output

| Output              | Formato     | Destinatario  |
|---------------------+-------------+---------------|
| Conferma operazione | Pagina HTML | Operatore     |
| Log modifica        | Record DB   | Audit interno |

***** Regole di business
- Un prodotto disattivato non appare nelle ricerche ma resta nel database per storico ordini
- Il codice SKU non è modificabile dopo la creazione
- La scorta minima determina la soglia per il job di allarme notturno
- Non è possibile eliminare un prodotto con ordini associati (solo disattivare)

***** Regole di validazione
- SKU: regex ~/^[A-Z]{2}-[0-9]{5}$/~, unicità verificata lato DB (UNIQUE constraint)
- Prezzo: conversione a centesimi interi per i calcoli, visualizzato con 2 decimali
- Categoria e fornitore: validati come FK esistenti

**** Import catalogo da SAP

***** Scopo
Importazione massiva di prodotti da file CSV generato da SAP Business One.
L'operatore carica manualmente il file tramite form web. I prodotti già
esistenti (match su SKU) vengono aggiornati; i nuovi vengono creati.

***** Input

| Campo    | Tipo di dato | Vincoli                           | Sorgente |
|----------+--------------+-----------------------------------+----------|
| File CSV | File upload  | Max 5 MB, encoding UTF-8 o Latin1 | SAP B1   |

Formato CSV atteso (header obbligatorio):

#+begin_example
SKU;Nome;Categoria;Prezzo;Peso;ScortaMinima;Fornitore
EL-00123;Cavo HDMI 2m;Cavi;12.50;0.150;20;TechCavi Srl
#+end_example

***** Output

| Output           | Formato     | Destinatario |
|------------------+-------------+--------------|
| Riepilogo import | Pagina HTML | Operatore    |
| Dettaglio errori | Tabella     | Operatore    |
| Log import       | Record DB   | Audit        |

***** Regole di business
- Separatore: punto e virgola (~;~)
- Encoding: auto-detect Latin1 → conversione a UTF-8
- Righe con errore vengono saltate, non bloccano l'import
- Il riepilogo mostra: N inseriti, N aggiornati, N errori, dettaglio errori per riga

*** Gestione Ordini

**** Ciclo di vita dell'ordine

***** Scopo
Gestisce l'intero ciclo di vita di un ordine, dalla ricezione alla spedizione.
Gli ordini possono essere inseriti manualmente o importati da SAP.

***** Stati dell'ordine

| Stato      | Descrizione                        | Transizioni possibili          |
|------------+------------------------------------+--------------------------------|
| nuovo      | Ordine appena inserito             | picking, annullato             |
| picking    | Prelievo articoli in corso         | packing, nuovo (rollback)      |
| packing    | Imballo e verifica completezza     | spedizione, picking (rollback) |
| spedizione | Bolla generata, tracking assegnato | completato                     |
| completato | Consegnato e confermato            | (stato finale)                 |
| annullato  | Ordine cancellato                  | (stato finale)                 |

***** Input

| Campo           | Tipo di dato | Vincoli                            | Sorgente  |
|-----------------+--------------+------------------------------------+-----------|
| Cliente         | FK           | Da tabella ~clienti~, obbligatorio | Operatore |
| Indirizzo sped. | Testo        | Obbligatorio                       | Operatore |
| Righe ordine    | Array        | Almeno 1 riga                      | Operatore |
| — Prodotto      | FK           | Prodotto attivo con giacenza > 0   | Operatore |
| — Quantità      | Intero       | >= 1                               | Operatore |
| — Prezzo        | Decimale     | Precompilato da anagrafica         | Sistema   |
| Note            | Testo        | Opzionale, max 500 caratteri       | Operatore |

***** Regole di business
- La giacenza viene decrementata al passaggio in stato ~packing~ (non prima)
- Il rollback da ~packing~ a ~picking~ ripristina le giacenze
- La bolla PDF viene generata al passaggio in stato ~spedizione~
- Il tracking BRT viene richiesto automaticamente dopo la generazione bolla
- L'email di conferma al cliente viene inviata dopo l'assegnazione del tracking
- Un ordine ~annullato~ non può essere riaperto (creare nuovo ordine)
