* Filling-in guide — arc42                                         :noexport:

This file documents the architecture of the component following the arc42 structure.  The sections start empty: when you write their content, mark it =[TO VALIDATE]= until a reliable source (code, logs, interview or document) confirms it, then replace the marker with =[APPROVED YYYY-MM-DD]= or =[FINDING]= depending on the outcome of the check.  While a section is empty, =blueprint-lint= reports the file as having no content.

Hierarchy of sources (most reliable first): code → tests → logs → monitoring → interviews → existing documentation.

=#+BLUEPRINT_STATUS:= is =in-scope= (default), =out-of-scope= or =tbd=.  An =out-of-scope= component is left out of the assessment but stays tracked (the reason goes in Part 0 of the master document); =blueprint-lint= reports an =in-scope= component that depends on an =out-of-scope= one.

=#+BLUEPRINT_LIFECYCLE:= is the life cycle of the component, an axis distinct from the scope: =draft=, =active= (default), =deprecated= or =archived=.  The dashboard shows it in the =Life= column; =blueprint-lint= reports an =active= component with open FIXMEs or depending on a =deprecated= one.

** What to write in each section

- /Introduction/: what the component does, whom it serves, its role in the architecture of the system.
- /Context and scope/: users and roles, neighboring systems (tables as in the examples above), boundaries of the component; C4 context diagram.
- /Constraints/: technical, organizational and regulatory constraints that affect the architectural choices (table as in the example above).
- /Solution strategy/: architectural principles, patterns adopted, relevant technology choices with their reasons (when they can be reconstructed).
- /Building blocks/: static view of the internal building blocks (C4 containers; C4 L3 if the complexity calls for it).
- /Runtime behavior/: the main flows at run time; for each flow the actors involved (use cases) and the detail of the messages exchanged (sequence).  =blueprint-runtime-add-flow= creates the subsection of a flow.
- /Business processes/: multi-actor processes relevant to the component, as a UML activity diagram with one swimlane per actor.  =blueprint-runtime-add-process= creates the subsection of a process.
- /Deployment/: environments, hosts, configuration; the detail goes in the infrastructure census (=infrastructure.org= next to this file).
- /Responsibility/: cross-cutting aspects (security, authentication, authorization, logging, error handling, transactions), table as in the example above.
- /Risks/: technical risks specific to the component; the cross-cutting ones go in the risk register of the project (=nfr/risks.org=).
- /Open questions/: questions raised during the analysis that need validation (=blueprint-add-question=).
- /Diagrams/: additional diagrams that fit none of the sections above.

* Introduction
:PROPERTIES:
:BLUEPRINT_SECTION: introduction
:END:
<<orders-intro>>

The orders module receives the orders exported by SAP Business One as CSV files on a network share, validates them and takes them to fulfillment: picking, packing, shipping request and invoice. It is the heart of WarehouseManager and the component with the most business logic.

* Context and scope
:PROPERTIES:
:BLUEPRINT_SECTION: context-scope
:END:
<<orders-context>>

In: the CSV of the orders from SAP B1, imported by hand by the operator twice a day. Out: the shipping request to the shipping module, the delivery note data to the invoicing module and the confirmation e-mails through the notifications module.

* Constraints
:PROPERTIES:
:BLUEPRINT_SECTION: constraints
:END:
<<orders-constraints>>

PHP 7.4, out of support since November 2022. Moving to PHP 8 means rewriting the calls to the =mysql_*= functions left in two files. [FINDING]

* Solution strategy
:PROPERTIES:
:BLUEPRINT_SECTION: solution-strategy
:END:
<<orders-strategy>>

Monolithic PHP application with no framework, one page per use case and the SQL queries written by hand inside the pages. There is no separate service layer. [TO VALIDATE]

* Building blocks
:PROPERTIES:
:BLUEPRINT_SECTION: building-blocks
:END:
<<orders-static>>

Three groups of files: import (reading and validating the CSV), fulfillment (order states and picking list) and printouts (delivery notes in PDF with FPDF).

* Runtime behavior
:PROPERTIES:
:BLUEPRINT_SECTION: runtime
:END:
<<orders-runtime>>

Fulfilling an order: the operator opens the order, confirms the picking, the system creates the delivery note, requests the shipment and sends the invoice, all inside one synchronous HTTP request.
