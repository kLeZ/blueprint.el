* Guida alla compilazione — Specifiche funzionali                  :noexport:

Questo file descrive il componente in termini di business, senza fare
assunzioni sulla tecnologia sottostante.  Il lettore di riferimento è
il /domain expert/ o il /product owner/, non il tecnico.

Struttura:
- *Aree funzionali*: macro-capacità del componente (es. "Gestione pagamenti")
- *Feature*: singola funzionalità con input, output e regole di business
- *Entità di dominio*: oggetti con cui il componente lavora
- *Punti di integrazione*: cosa entra e cosa esce, in linguaggio di business

** Esempio: area funzionale e feature                              :noexport:

*** Autorizzazione pagamento

**** Scopo
Verifica che un pagamento possa essere processato e ne avvia
l'autorizzazione presso il provider.  Restituisce l'esito (autorizzato /
rifiutato) al chiamante entro i termini di latenza contrattualmente
definiti.

**** Input
| Nome (business)     | Tipo (business)  | Vincoli                        | Provenienza   |
|---------------------+------------------+--------------------------------+---------------|
| Importo             | Valore monetario | > 0,01 €; max 9.999,99 €       | order-service |
| Valuta              | Codice ISO 4217  | Solo EUR e USD supportati      | order-service |
| Metodo di pagamento | Identificatore   | Token Stripe; mai dati carta   | order-service |
| Idempotency key     | Stringa UUID     | Univoca per richiesta; 24h TTL | order-service |

**** Output
| Nome (business) | Tipo (business) | Formato        | Destinazione  |
|-----------------+-----------------+----------------+---------------|
| Esito           | Enum            | authorized /   | order-service |
|                 |                 | declined /     |               |
|                 |                 | error          |               |
| Codice risposta | Stringa         | Stripe decline | order-service |
|                 | descrittiva     | codes (es.     |               |
|                 |                 | insufficient_  |               |
|                 |                 | funds)         |               |

**** Regole di business
1. Un pagamento con la stessa idempotency key già elaborata nelle ultime
   24 h restituisce l'esito originale senza ri-autorizzare.
2. Se Stripe risponde con errore transitorio (=HTTP 500/503=), il sistema
   effettua al massimo 3 tentativi con backoff esponenziale (1 s, 2 s, 4 s).
3. Importi superiori a 1.000 € richiedono verifica 3DS2 obbligatoria.

**** Logica di calcolo
Nessuna logica di calcolo: la decisione di autorizzazione è delegata
interamente al provider (Stripe).  Il sistema è un orchestratore.

**** Regole di validazione
| Condizione              | Comportamento / Errore                      |
|-------------------------+---------------------------------------------|
| Importo ≤ 0             | =HTTP 400= — "importo non valido"           |
| Valuta non supportata   | =HTTP 422= — "valuta non supportata"        |
| Idempotency key assente | =HTTP 400= — "idempotency key obbligatoria" |

**** Casi limite e eccezioni
- Timeout Stripe (> 30 s): restituire =error= al chiamante; registrare
  la transazione come =pending= per verifica asincrona tramite webhook.
- Provider non raggiungibile (circuit breaker aperto): restituire =error=
  con motivo =provider_unavailable=; non ritentare oltre i 3 tentativi.

** Esempio: entità di dominio                                      :noexport:

*** Transazione

Registrazione immutabile di un tentativo di pagamento, indipendentemente
dall'esito.  Corrisponde a una singola chiamata al provider.

| Attributo          | Tipo (business)  | Vincoli               | Relazione | Note                         |
|--------------------+------------------+-----------------------+-----------+------------------------------|
| ID transazione     | UUID             | Generato internamente |           |                              |
| Idempotency key    | Stringa          | Fornita dal chiamante |           |                              |
| Importo            | Valore monetario | > 0                   |           |                              |
| Valuta             | Codice ISO 4217  |                       |           |                              |
| Stato              | Enum             | authorized/declined/  |           | Immutabile dopo assegnazione |
|                    |                  | pending/error         |           |                              |
| Riferimento ordine | UUID             |                       | → Ordine  | Chiave esterna logica        |
| Timestamp          | Data/ora UTC     |                       |           |                              |

** Esempio: punto di integrazione                                  :noexport:

*** Ricezione richiesta da order-service

Descrizione: l'=order-service= chiama il =payment-service= in modo sincrono
per richiedere l'autorizzazione di un pagamento associato a un ordine
confermato.

| Campo          | Valore                                         |
|----------------+------------------------------------------------|
| Direzione      | IN                                             |
| Controparte    | order-service                                  |
| Protocollo     | REST / HTTPS / HTTP 2                          |
| Autenticazione | mTLS (certificato client del chiamante)        |
| Frequenza      | Sincrona — una chiamata per ordine confermato  |
| SLA            | Risposta entro 5 s; timeout client impostato a |
|                | 8 s per includere i retry interni              |

**** Formato scambio

Struttura del payload in ingresso.

#+begin_src json
{
  "idempotency_key": "ord-20240215-78fa3c",
  "amount": 4950,
  "currency": "EUR",
  "payment_method_token": "pm_1OdXXXXX",
  "order_reference": "ORD-2024-001847"
}
#+end_src

** Cosa scrivere in ogni sezione                                   :noexport:

Le sezioni nascono vuote.  Quando se ne scrive il contenuto, marcarla con
=[DA VALIDARE]= fino alla conferma da una fonte attendibile.

- /Panoramica del componente/: scopo del componente in termini di business,
  quale problema risolve, a quale dominio funzionale appartiene.
- /Aree funzionali/: una sottosezione per area (=blueprint-functional-add-area=),
  con le feature al suo interno (=blueprint-functional-add-feature=): scopo,
  input, output, regole di business, logica di calcolo (notazione matematica
  con variabili in linguaggio di dominio, es.
  =Importo_Netto = Importo_Lordo * (1 - Aliquota_IVA)=), regole di
  validazione, casi limite ed eccezioni.
- /Entità di dominio/: oggetti di dominio con attributi in linguaggio business,
  non tabelle del DB (=blueprint-functional-add-entity=).  La colonna
  /Relazione/ indica l'entità target degli attributi che sono chiavi esterne
  (es.: ~→ Ordine~).  In coda, un diagramma ER generale del componente.
- /Punti di integrazione/: cosa il componente riceve da e invia ad altri
  sistemi, in termini di business: una tabella riassuntiva e una
  sottosezione per integrazione (=blueprint-functional-add-integration=).
- /Flussi dati/: Data Flow Diagram (notazione Yourdon/DeMarco) per il data
  lineage: da dove arrivano i dati, quali processi li trasformano, dove
  vengono persistiti e verso quali sistemi escono.  Complementa la tabella
  dei punti di integrazione con il percorso del dato.
- /Open Questions/: elementi non determinabili dal codice che richiedono
  validazione con il domain expert.
