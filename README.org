#+TITLE: Blueprint

Text-first architectural assessment toolkit for GNU Emacs.

Blueprint helps software architects and technical leads document, visualize, and
assess software architecture directly from Emacs using plain-text Org-mode
files. It follows a component-based approach inspired by the
[[https://arc42.org/][Arc42]] documentation methodology and produces
[[https://c4model.com/][C4 model]] diagrams via PlantUML.

* Background and rationale
Blueprint started life as a Python CLI tool (=scaffold.py=) for generating and
managing Arc42-based assessment documents. The Python version handled project
initialization, component CRUD, glossary management, status reporting (tag
scanning), master-file synchronization, and export via Pandoc.

The rewrite in Emacs Lisp was motivated by a single observation: the entire
workflow already lived inside Emacs and Org mode. Shelling out to Python for
file manipulation that Org can do natively was unnecessary friction. The goals
for the Emacs port were:

1. *Full feature parity* with the Python original --- no "MVP, we'll see later"
   compromises.
2. *Idiomatic Emacs Lisp* --- leverage =org-element= AST parsing instead of
   fragile regex hacks, use the native Org exporter instead of Pandoc, and
   integrate with Transient for a discoverable UI.
3. *Zero mandatory external dependencies* --- only Emacs 29+ and the bundled
   Transient library are required. PlantUML and Graphviz are optional for
   rendering.
4. *Offline-first, text-first, versionable* --- every artifact is plain text. No
   databases, no cloud services, no lock-in.

The name changed from "scaffold" (too generic, evokes CRUD generators) to
*blueprint* --- cleaner, more architectural, and appropriate for a tool that
helps you reason about software structure.

* Design decisions
** Why Transient instead of plain keybindings
Raw keybindings (=C-c s a=, =C-c s r=, =C-c s q=, ...) are invisible, not
discoverable, and hard to remember after two weeks away from the project.
[[https://magit.vc/manual/transient/][Transient]] --- the same framework behind
Magit --- provides a self-documenting popup menu with logical groups. One
keybinding (=C-c b=) opens the entire command surface.

This is the same UX pattern that makes Magit feel like a "real tool" rather than
a collection of scattered commands.

** Three-tier template system
Templates *cannot* be hardcoded in the package. During a typical 12-day
co-design engagement with a client, the skeleton documents evolve continuously.
Blueprint solves this with a three-tier resolution order:

| Priority | Location                         | Purpose                           |
|----------+----------------------------------+-----------------------------------|
| 1        | =.blueprint/templates/=          | Project-local overrides           |
| 2        | =~/.config/blueprint/templates/= | Personal defaults across projects |
| 3        | =templates/= in package dir      | System fallback (read-only)       |

The first match wins. You can clone system defaults into a project
(=blueprint-template-migrate=), customize them for the engagement, and version
them alongside the assessment. The system defaults remain untouched as a
fallback.

** Component-based structure
Each component gets its own directory under =.blueprint/components/= with an
=arc42.org= file. This keeps concerns separated and allows the master document
to assemble components via =#+INCLUDE:= directives. Dependencies between
components are declared with a simple Org keyword:

#+begin_src org
,#+BLUEPRINT_DEPENDS: auth database cache
#+end_src

These declarations are parsed to generate C4 container diagrams --- no manual
diagramming required.

** Health scoring as motivation
The health score (0--100) penalizes markers like =QUESTION=, =TBD=, and =FIXME= left in the document (=master.org= and every file it includes), relative to how much text it contains. It is intentionally simple --- a gamified nudge to clean
up open items rather than a rigorous metric. The SVG gauge makes it visual
enough to show a client during a review session.

* Features
- *Project initialization* --- creates =.blueprint/= directory structure with
  =components/= and =adr/= subdirectories
- *Component management* --- full CRUD: add, list, rename, and delete
  components, each with up to three documents: =arc42.org= (Parte II), =functional.org= (Parte III) and =infrastructure.org= (Parte IV). The component list (=l=), the dashboard and =blueprint-visit-component= (=j=) open any of the three
- *Component skeleton wizard* --- interactive prompts for name, responsibility,
  owner, and tech stack that pre-fill the template
- *Wizard onboarding* --- guided step-by-step project setup
- *C4 diagram generation* --- produces PlantUML C4 container diagrams by parsing
  =#+BLUEPRINT_DEPENDS:= keywords from component files
- *Dependency graph* --- PlantUML/Graphviz visualization of component dependencies (=G=); Graphviz nodes are colored by each component's health score over its documents in =master.org=. =h= draws the same colored graph with Graphviz whatever the backend
- *Health score gauge* --- calculates a quality score and renders it as an SVG
  semicircular gauge with metrics caching
- *Dashboard buffer* --- Magit-style status buffer with one row per component and one per other file of the document (master.org, glossary, Parte I and V, references): Owner, Tech stack, Scope, marker counts, penalty points, health score and Status, navigable with =RET= to open the row's file
- *Focus mode* --- filtered dashboard showing only components that need
  attention
- *SVG dashboard* --- Graphviz-based visual overview with risk-based coloring
- *Glossary management* --- structured glossary with terms, definitions, and
  source attribution
- *Reference tracking* --- document, interview, and system references
- *Open questions* --- AST-based insertion into component =arc42.org= files
  using =org-element= (no regex)
- *Master file sync* --- automatic synchronization of =#+INCLUDE:= directives in
  the master document
- *Linter* --- validation rules (missing headings, excessive unresolved markers,
  dangling dependencies, empty content) with headless/CI support
- *Org-native export* --- PDF, ODT, HTML, and DOCX export using the Org
  exporter (DOCX requires =ox-pandoc=); ODT respects a per-file
  =#+ODT_STYLES_FILE:= corporate template. =blueprint-export-dispatch= hands
  off to Org's own =org-export-dispatch= menu to pick a backend/template
  interactively instead of using the fixed default (=blueprint-export-backend=,
  =pdf= unless overridden)
- *ODT styles check* --- =blueprint-check-odt-styles= catches a corporate
  =#+ODT_STYLES_FILE:= template that silently drops an Org-internal style
  (images overlapping text with no error anywhere); CI entry point
  =blueprint-ci-check-odt-styles=
- *Async tangle/export* --- background processing via Emacs 29+ threads to avoid
  blocking the UI
- *Auto-tangle on save* --- minor mode for automatic =org-babel-tangle= when
  saving =.org= files in a Blueprint project
- *Watch mode* --- =after-save-hook= minor mode for automatic cache
  invalidation, master sync, and C4 regeneration
- *Rule-based risk suggestions* --- deterministic pattern matching against
  component text to suggest common architectural risks (single point of failure,
  unclear ownership, missing monitoring, etc.)
- *AI-assisted snippets (Ollama)* --- optional local LLM integration for section
  expansion, risk suggestion, and boilerplate generation. Fully offline, no data
  leaves the machine. Falls back to rule-based suggestions when Ollama is not
  running
- *Prompt guardrails* --- context clamping, character limits, and sanitization
  (emails, IPs, passwords) for LLM prompts
- *Architecture Decision Records (ADR)* --- automatic ADR creation and
  management in =.blueprint/adr/= with numbered files and status tracking
- *Ripgrep search* --- project-wide search with predefined queries for open
  questions, TBDs, and FIXMEs (falls back to grep)
- *Quick capture* --- =org-capture=-style note taking for notes, questions, and
  glossary terms
- *Daily workflow command* --- one-key triage sequence (dashboard → focus → select component, ordered by penalty points over all its documents → select document → edit)
- *Org-roam integration* --- components as navigable org-roam nodes with
  backlink support (requires =org-roam=)
- *Incremental functional spec* --- four commands to build =functional.org=
  piece by piece: add a functional area, add a feature (full skeleton: Scopo,
  Input, Output, Regole di business, Regole di validazione, Casi limite), add a
  domain entity with attribute table and PlantUML ER skeleton, or add an
  integration point with metadata table and payload block. Designed for large
  components and monoliths
- *Runtime flow documentation* --- =blueprint-runtime-add-flow= adds a named
  runtime flow to =arc42.org= with two views: use-case diagram (for
  non-technical stakeholders) and sequence diagram (for engineers)
- *NFR management* --- three commands to populate NFR files incrementally:
  =blueprint-nfr-add-quality-scenario= (arc42-style scenario with attribute /
  context / stimulus / expected response / measure),
  =blueprint-nfr-add-constraint= (technical / organizational / regulatory),
  =blueprint-nfr-add-risk= (auto-incremented R-NNN ID, automatic level
  calculation from probability × impact matrix)
- *Methodology marker tracking* --- =blueprint-list-findings= and
  =blueprint-list-unvalidated= scan all Org files project-wide and display
  results in a navigable read-only buffer with file and line references
- *Pre-delivery check* --- =blueprint-pre-delivery-check= runs all automatable readiness checks (health score, unresolved =[DA VALIDARE]= and =[DA REVISIONARE]= markers, lint warnings, master sync status) and produces a pass/warn report; the =[FINDING]= count is shown for information only and never affects the outcome
- *CI/headless mode* --- =emacs --batch= entry points for linting, validation,
  and export with appropriate exit codes
- *Metrics caching* --- MD5-based hash-table cache invalidated on file change
  for instant dashboard rendering on large projects
- *Template system* --- three-tier hierarchy with diff and non-destructive
  migration tools
- *Transient menu* --- all commands accessible through =C-c b=

* Quick start
1. Open a directory in Emacs where you want to create an architecture project.
2. Run =M-x blueprint-wizard-init= (or =C-c b W=) for a guided setup, or
   =M-x blueprint-init= (or =C-c b I=) for manual initialization.
3. Add a component with =M-x blueprint-add-component= (or =C-c b A=) for a
   simple component, or =M-x blueprint-wizard-component= (=C-c b w=) for a
   pre-filled wizard.
4. Edit the =arc42.org= file to document the component's responsibility, risks,
   questions, and dependencies.
5. Declare dependencies with =#+BLUEPRINT_DEPENDS: other-component=.
6. Open the dashboard with =C-c b B= to see all components at a glance.
7. Generate a C4 diagram with =C-c b C=, a dependency graph with =C-c b G=, the
   health-colored component graph with =C-c b h=, or a health SVG with =C-c b H=.
8. Run =C-c b L= to lint the project, =C-c b s= for risk suggestions.

** Initializing a project
=blueprint-init= creates the following structure in the current directory:

#+begin_example
.blueprint/
├── components/               # One subdirectory per component
├── adr/                      # Architecture Decision Records
├── templates/                # Local template overrides (copied from system)
├── enterprise/
│   ├── enterprise-context.org
│   └── enterprise-dependencies.org
├── nfr/
│   ├── nfr-quality.org
│   ├── nfr-constraints.org
│   └── nfr-risks.org
├── _archive/                 # Archived content
├── glossary.org              # Project glossary
└── references.org            # Sources and references
master.org                    # Six-part assessment deliverable
#+end_example

*Template provisioning*: the first time =blueprint-init= is called
interactively, it checks whether user-level templates exist at
=~/.config/blueprint/templates/=. If any template file is missing, Blueprint
copies all system defaults there and displays a message listing every file
written to your home directory. This ensures you always have an editable copy of
the templates at the user level, independent of the package installation.

#+begin_quote
*Note*: provisioning only runs when called interactively. Batch mode and
automated tests are never affected.
#+end_quote

** Data directory name
The per-project data directory (components, ADRs, local templates) is
=.blueprint/= by default. Set =blueprint-directory-name= to use a different
name, or a nested relative path such as =content/blueprint=, when the project
layout has to match what a site generator or build tool expects. Set it
globally (init file or =customize=). It is also marked safe as a
directory-local variable, but a =.dir-locals.el= value only reaches buffers
visiting a project file: commands run from buffers that visit no file (the
dashboard, result buffers) still see the global value.

A project that still has =.blueprint/= keeps working after the variable
changes: Blueprint falls back to it and warns once per session. To rename it,
run =blueprint-migrate-directory= (=C-c b m=). It shows the plan and asks for
confirmation, then renames the directory (with =git mv= when git tracks it)
and rewrites every file link and =#+INCLUDE:=/=#+SETUPFILE:= path in the
project's Org files that the rename would break, including links from files
inside the moved directory to files outside it. Plain-text mentions (prose,
=:file= arguments of source blocks) are only listed in the report buffer.

** Adding components
=blueprint-add-component= prompts for a component name and creates:

#+begin_example
.blueprint/components/<slug>/
├── arc42.org          # Arc42 architectural view (from template)
├── functional.org     # Technology-agnostic functional spec (when template exists)
└── infrastructure.org # Infrastructure census (when template exists)
#+end_example

The component name is slugified (lowercase, hyphens only) to produce the
directory name and the ={{ID}}= placeholder used in PlantUML diagram IDs.

The =arc42.org= template contains full Arc42 sections (Introduction, Context and
Scope, Constraints, Solution Strategy, Building Blocks, Runtime Behavior,
Processi di business, Deployment, Responsibility, Risks, Open Questions,
Diagrams), plus =#+BLUEPRINT_DEPENDS:=, =#+BLUEPRINT_OWNER:=,
=#+BLUEPRINT_TECH:=, and =#+BLUEPRINT_STATUS:= keywords.

** Declaring dependencies
In any component's =arc42.org= file, list space-separated dependency names:

#+begin_src org
,#+BLUEPRINT_DEPENDS: auth database
#+end_src

These are parsed by the C4 generator to produce relationship arrows.

** Marking a component out of scope
=#+BLUEPRINT_STATUS: in-scope | out-of-scope | tbd= (defaults to =in-scope=
when absent) marks a component's assessment perimeter status. =blueprint-lint=
warns when an =in-scope= component depends on an =out-of-scope= one; the
dashboard's Scope column and out-of-scope filter (=O=, or
=blueprint-out-of-scope-view=) read the same keyword. Document the reason a
component is excluded in Part 0 of =master.org= --- the keyword only tracks
the status, not the rationale.

** Generating C4 diagrams
=blueprint-generate-c4= reads all components and their =#+BLUEPRINT_DEPENDS:=
keywords, then writes a =c4.puml= file to the project root. The output uses
PlantUML's C4 Container syntax:

#+begin_src plantuml
@startuml
!include C4_Container.puml
Container(api, "api", "component")
Container(auth, "auth", "component")
Rel(api, auth, "uses")
@enduml
#+end_src

Render with PlantUML or a compatible tool.

=blueprint-generate-enterprise-c4= is the simpler, enterprise-wide
counterpart: it writes a C4 L1 context diagram (=System(...)= per
component, =Rel(...)= per dependency, no =Container=) into the
auto-generated section of =enterprise/context.org=, leaving anything you
wrote by hand outside that section --- external systems, users, relations
to them --- untouched on every regeneration, the same way =blueprint-sync=
preserves manual content in =master.org=.

** Health scoring
=blueprint-health-score= weighs the open markers found in the document: =master.org= and every file it includes with =#+INCLUDE:=, recursively, each path resolved against the file that includes it. Parte 0 (the text of =master.org=), the glossary, Parte I, the component documents, Parte V and the references all count; files =master.org= does not include (notes, knowledge base, a component document not synced yet) do not. Every count of the package uses the same files: dashboard, pre-delivery check, lint, risks and the marker lists.

| Marker             | Weight | Meaning                                   |
|--------------------+--------+-------------------------------------------|
| =QUESTION=         | 3      | Unresolved architectural question         |
| =TBD=              | 2      | To-be-determined item                     |
| =FIXME=            | 4      | Known defect or urgent issue              |
| =[DA VALIDARE]=    | 1      | Section not yet confirmed by stakeholders |
| =[DA REVISIONARE]= | 1      | Needs re-review after a change            |
| =[FINDING]=        | 0      | Confirmed discrepancy from primary source |

=[FINDING]= weighs 0: a finding is a result the assessment delivers, not an open point. It is still listed by =blueprint-list-findings= and counted by the metrics.

The weighted sum P is set against the size of the same files, so the score does not fall just because the document grows. With W the number of words of exported text (same exclusions as the markers, see below) and N the custom variable =blueprint-health-words-per-point= (default 100):

#+begin_example
U     = W / N
score = round(100 * U / (U + P))
#+end_example

The score is 50 with one penalty point every N words, higher with fewer. P = 0 gives 100 (also for an empty project); P > 0 with no words gives 0. Doubling the document with the same share of markers leaves the score unchanged. Called interactively, the command also shows P and W in the echo area. The score is computed on every call, with one parse per file.

Markers count only where the export shows them as live text. Blueprint skips
subtrees with an export exclude tag (=:noexport:= or anything in
=#+EXCLUDE_TAGS:=), COMMENT subtrees, src/example/export/comment blocks,
comment lines and verbatim/code markup (==[FINDING]== names the marker without
being one). Matching is case-sensitive, so "question" in prose is not a
=QUESTION=. File keywords such as =#+STATUS: [DA VALIDARE]= still count. The
same rule applies to the lint marker threshold, the marker lists, the
pre-delivery check and =blueprint-list-questions=.

An =#+INCLUDE:= inside a non-exported subtree or a comment is not followed, and a file included as a block (=src=, =example=, =export=) does not count, since it is code in the document. Known limits: a file included only in part (=:lines=, =file.org::*Heading=) counts whole, a file included twice counts once, =#+EXCLUDE_TAGS:= applies only to the file that declares it (the exporter applies master.org's to the whole document) and =#+SELECT_TAGS:= is not supported. Without =master.org= the counts use the documents of every component, as =blueprint-sync= would include them.

Two additional commands list methodology markers in the document:

- =blueprint-list-findings= (=C-c b g=) --- all =[FINDING]= occurrences
- =blueprint-list-unvalidated= (=C-c b u=) --- all =[DA VALIDARE]= sections

=blueprint-health-svg= generates a semicircular gauge as an SVG file
(=health.svg=) in the project root and shows it in the =*Blueprint Health*=
buffer. The file is a standalone SVG with its own white background, so it
can be opened in a browser or dropped into a document for the client.

** Dashboard
=blueprint-dashboard= opens a =tabulated-list-mode= buffer with one row per component, in alphabetical order, then one row per other file of the document in the order =master.org= includes it (=master.org= itself, glossary, =enterprise/*=, =nfr/*=, references), named by its path relative to the root. Every file of the document is in exactly one row, so the rows add up to the health score of the whole document. The header line holds the column titles, aligned with the rows also when line numbers are displayed; the mode line shows the document's health score, the number of components and of other files, and the active filters.

Columns: Name; Owner (=#+BLUEPRINT_OWNER:=), Tech (=#+BLUEPRINT_TECH:=) and Scope (=#+BLUEPRINT_STATUS:=) from a component's =arc42.org=; the counts of =QUESTION=, =TBD=, =FIXME=, =[DA VALIDARE]= (DA VAL), =[DA REVISIONARE]= (DA REV) and =[FINDING]=; Penalty and Health, with the weights and formula of =blueprint-health-score= applied to the row alone (=[FINDING]= is counted but weighs 0); Status. A component row counts only its documents included in =master.org=. Status is =FIXME=, =NEEDS-WORK= (more than two =QUESTION=), =IN-PROGRESS= (any other open marker, methodology markers included), =OK=, or =NOT-INCLUDED= for a component none of whose documents is in =master.org= (Health shows =-=).

Navigation: =RET= opens the row's file (for a component with more than one document, it asks which, =arc42.org= preselected), =g= refreshes, =F= toggles focus mode (rows with penalty points and =NOT-INCLUDED= components, so a row with only =[FINDING]= is hidden), =O= toggles the out-of-scope filter (show only =out-of-scope=/=tbd= components), =G= draws the colored graph (=blueprint-dashboard-svg=), =q= closes. Numeric columns sort by value.

The same per-component figures drive the other views. =blueprint-dashboard-svg= (=C-c b h=) and the Graphviz dependency graph color each node by its score: red below 50 (the =blueprint-ci-validate= warning threshold), yellow below 80 (the default =blueprint-delivery-score-threshold=), green otherwise, grey when =master.org= includes none of the component's documents. With the default =blueprint-graph-backend= (=plantuml=), =C-c b G= writes an uncolored =.puml=. =blueprint-daily= lists the components and the other files with penalty points, most first; for a component it then asks which document to open, preselecting the one with most penalty points.

The component list (=blueprint-list-components=, =l=) shows which documents each component has: =RET= asks which one to open, =a=, =f= and =i= open =arc42.org=, =functional.org= and =infrastructure.org= directly. =blueprint-visit-component= (=j=) does the same from anywhere, and =blueprint-list-questions= collects =- QUESTION= items from all three documents.

** Template management
Blueprint uses a three-tier template resolution order:

1. *Project templates* --- =.blueprint/templates/= in the project root
2. *User templates* --- =~/.config/blueprint/templates/=
3. *System templates* --- =templates/= in the Blueprint package directory

When resolving a template, the first match wins. This allows projects and users
to override system defaults without modifying the package.

Available templates:

| Template                      | Purpose                                      |
|-------------------------------+----------------------------------------------|
| =component.org=               | Arc42 architectural view per component       |
| =functional.org=              | Technology-agnostic functional specification |
| =infrastructure.org=          | Infrastructure and deployment census         |
| =master.org=                  | Six-part assessment deliverable              |
| =adr.org=                     | Architecture Decision Record                 |
| =glossary.org=                | Project glossary                             |
| =references.org=              | Sources and references                       |
| =enterprise-context.org=      | Enterprise system context (L1 C4)            |
| =enterprise-dependencies.org= | Inter-system dependencies                    |
| =nfr-quality.org=             | Non-functional quality requirements          |
| =nfr-constraints.org=         | Technical and organizational constraints     |
| =nfr-risks.org=               | Project-level risks and mitigations          |

- =blueprint-template-diff= --- shows a unified diff between system and project
  templates (read-only)
- =blueprint-template-migrate= --- copies missing template files from system
  defaults into the project (never overwrites existing files)
- =blueprint-migrate-directory= --- renames the project data directory to
  =blueprint-directory-name= and fixes the paths into it (see
  [[*Data directory name][Data directory name]])

** Master file sync
=blueprint-sync= manages three independent =#+INCLUDE:= sections in
=master.org=, each delimited by a pair of comment markers:

| Section                       | Start marker                          | File synced          |
|-------------------------------+---------------------------------------+----------------------|
| Arc42 architecture (Parte II) | =@@blueprint-sync-start@@=            | =arc42.org=          |
| Functional specs (Parte III)  | =@@blueprint-sync-functional-start@@= | =functional.org=     |
| Infrastructure (Parte IV)     | =@@blueprint-sync-infra-start@@=      | =infrastructure.org= |

If a marker pair is absent from =master.org=, that section is silently skipped ---
backward compatible with projects using only the original arc42 markers.
Components without the corresponding file are also skipped.

** Incremental functional spec
For large components --- monoliths, complex services with many features --- the
blank =functional.org= template can be overwhelming. Three commands let you
build it incrementally, one piece at a time:

| Command                                | Key | What it adds                                                                                                                                                           |
|----------------------------------------+-----+------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| =blueprint-functional-add-area=        | =a= | Level-2 heading under =* Aree funzionali= with org anchor and =[DA VALIDARE]= placeholder                                                                              |
| =blueprint-functional-add-feature=     | =f= | Level-3 feature skeleton under a chosen area: Scopo, Input, Output, Regole di business, Regole di validazione, Casi limite e eccezioni                                 |
| =blueprint-functional-add-entity=      | =e= | Level-2 heading under =* Entità di dominio= with attribute table and =*** Rappresentazione logica= with PlantUML ER skeleton                                           |
| =blueprint-functional-add-integration= | =i= | Level-2 heading under =* Punti di integrazione= with metadata table (direction, counterpart, protocol, auth, frequency, SLA) and =*** Formato scambio= with code block |

=blueprint-functional-add-feature= offers a =completing-read= of the areas
already present in the file, so you cannot accidentally target a non-existent
area. Missing sections (=* Aree funzionali=, =* Entità di dominio=,
=* Punti di integrazione=) are created automatically if absent.

After each command the buffer is opened and the cursor is positioned at the
newly inserted content.

** CI / headless usage
Blueprint provides dedicated batch-mode entry points with exit codes:

#+begin_src sh
# Lint all components (exit 0=pass, 1=warnings)
emacs -Q --batch -l blueprint.el -f blueprint-ci-lint

# Full validation: lint + health + dependency check (0=pass, 1=warn, 2=error)
emacs -Q --batch -l blueprint.el -f blueprint-ci-validate

# Export (exit 0=pass, 2=error)
emacs -Q --batch -l blueprint.el -f blueprint-ci-export

# ODT styles check (exit 0=pass, 2=missing styles found) -- opt-in, not
# part of blueprint-ci-validate: only meaningful when master.org sets a
# corporate #+ODT_STYLES_FILE:, and requires a real ODT export plus unzip
emacs -Q --batch -l blueprint.el -f blueprint-ci-check-odt-styles
#+end_src

** AI-assisted snippets
When Ollama is running locally, Blueprint can use it for:

- =blueprint-ai-expand= --- expand the current section with AI-generated content
- =blueprint-ai-suggest-risks= --- suggest architectural risks (falls back to
  rule-based suggestions when Ollama is unavailable)
- =blueprint-ai-boilerplate= --- generate professional boilerplate for empty
  sections

All prompts include guardrails: context clamping to =blueprint-ai-max-context=
characters, and sanitization of emails, IP addresses, and password-like
patterns.

* Assessment methodology
Blueprint implements the methodology documented in
=assessment-framework/methodology/METHOD.org=. The assessment is organized
around a strict information-source hierarchy:

1. *Source code* --- the ground truth; behavior that deviates from other sources
   is a finding
2. *Automated tests* --- reveal intended contracts
3. *Execution logs and monitoring* --- expose runtime behavior
4. *Direct interviews* --- stakeholder intent and tribal knowledge
5. *Pre-existing documentation* --- lowest priority; may describe desired rather
   than actual behavior

** Document structure
The =master.org= deliverable follows a six-part structure targeting different
audiences:

| Part      | Title                             | Audience                         |
|-----------+-----------------------------------+----------------------------------|
| Parte 0   | Premesse                          | All --- methodology, conventions |
| Parte I   | Architettura enterprise           | Executives, CTO                  |
| Parte II  | Architettura per componente       | Technical architects             |
| Parte III | Specifiche funzionali             | Business analysts, product       |
| Parte IV  | Censimento infrastrutturale       | Operations, SRE                  |
| Parte V   | Requisiti non funzionali e rischi | Management, project leads        |

** Marking conventions
Templates use Italian validation markers to track information quality:

| Marker                   | Meaning                                           |
|--------------------------+---------------------------------------------------|
| =[DA VALIDARE]=          | Not yet confirmed --- needs stakeholder review    |
| =[FINDING]=              | Confirmed observation from primary sources        |
| =[DA REVISIONARE]=       | Needs re-review after a change or new information |
| =[APPROVATO YYYY-MM-DD]= | Formally approved by stakeholders                 |
| =[FONTE: X]=             | Source attribution (code, interview, log, etc.)   |

These markers are searchable and provide an audit trail of the assessment
process.

* Contributing
Contributions are welcome. The guiding principles for this project:

- *Keep it simple* --- each module should be understandable in minutes.
- *No external runtime dependencies* --- PlantUML, Graphviz, Ollama, and
  org-roam are optional backends, not requirements.
- *Text-first* --- every artifact must be plain text and version-control
  friendly.
- *Emacs-idiomatic* --- use =org-element= over regex when parsing Org files, use
  Transient for UI, use =defcustom= for configuration.
